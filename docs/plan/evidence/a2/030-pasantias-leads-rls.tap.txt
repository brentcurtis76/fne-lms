freshly initialised local database, including the grant-list privilege hardening.
Command: psql -X -q -t -f supabase/tests/030-pasantias-leads-rls.sql (tuples-only, to expose every assert)

Round r3 grew the plan 30 → 32 and changed the *kind* of evidence behind asserts
4 and 5. They previously read `information_schema.role_table_grants`, a
SQL-standard view that reports only standard privileges — which is precisely how
round r2's pin failed to notice that PostgreSQL 17's `MAINTAIN` was not covered
by the enumerated REVOKE. They now read the real ACL via
`aclexplode(pg_class.relacl)`, so any privilege the server defines — standard,
PostgreSQL-specific, or added by a future release — is inside the assertion.
Asserts 8 and 9 are the new, version-guarded `MAINTAIN` probes.

## Server version — the asserts run LIVE here, they do not skip

The local and CI stacks are **PostgreSQL 17.6**: `supabase/config.toml` pins no
`[db] major_version`, so the Supabase CLI's default image applies, and CI gate 3
uses the same unpinned `supabase/setup-cli@v1`. `MAINTAIN` therefore genuinely
exists on the server this evidence was produced on, and asserts 8–9 execute
rather than skip. The hosted production database is 15.8 and takes the skip
branch. The 15.8 path is proven separately below.

## The sub-PostgreSQL-17 path, proven separately

Asserts 8–9 run live here, so the branch production (15.8) will take was proven
with a scratch script — not committed, not part of the suite — that reuses the
suite's exact CASE expressions with the version threshold raised so the ELSE
branch is taken on this PG17 server, plus a third assert proving the guard is
lazy. Laziness is the property that makes the suite runnable against a pre-17
server at all: `has_table_privilege(..., 'MAINTAIN')` raises "unrecognized
privilege type" there, so the call must not be evaluated when the guard is false.
The call is wrapped in a plpgsql function (`pg_temp.lacks_maintain`) rather than
written inline for exactly this reason — plpgsql functions are never folded into
the plan.

```
1..3
ok 1 # SKIP MAINTAIN does not exist below PostgreSQL 17 (server is 17.6) — the grant-list REVOKE ALL covers it on upgrade
ok 2 # SKIP MAINTAIN does not exist below PostgreSQL 17 (server is 17.6) — the grant-list REVOKE ALL covers it on upgrade
ok 3 - version guard is lazy: the PG17-only call is not evaluated when the guard is false
```

(The "server is 17.6" text is the real `current_setting('server_version')` of the
machine this ran on; against production the same string would read 15.8. The
threshold in the scratch script was 990000 solely to force the branch.)
