All four A9 tests appear in the run log by name, on a production build against the seeded stack:

```

✓ the optional marketing opt-in is recorded only when the visitor clicks it (652ms)

```

Test 1 is the one that could not be proven anywhere else. It is the only place the claim-and-release
contract in `lib/pasantias/emails.ts` has executed: CI carries no `RESEND_API_KEY`, so
`sendLeadAutoReply` returns `{sent:false, failure:'not_configured'}` and `runAutoReply` must restore
the previous value. `brochure_sent_at` came back `null` — a lead is not stamped "brochure sent" when
nobody was mailed. Test 3 is the **control**: A8 seeds a permanent `pasantiasLead` fixture and
`pasantias-leads-admin.spec.ts` is read-only on it by design, so A9 asserting the fixture is
unchanged is what proves A9's spec did not quietly break A8's guard. A8's three tests ran green in
the same job, from the other direction.

**What it did not prove.** This is the code-bearing run, and what it establishes is that the four
tests pass against a freshly seeded stack. It is not evidence of **robustness to change**: it and
every run listed below executed the **same code** against the **same seeded fixture set**, so their
agreement demonstrates determinism, not that the spec would survive a change to the code it guards.
And it says nothing at all about the four OWNER-RUN rows (A2-9, A2-11, A2-12, A2-13), which need a
real mailbox and a real handset.

## Why the guard says 12 when `MANDATORY_SPECS` has 11 entries

Not a discrepancy. CI builds the PR's **merge** commit, and `main` had advanced past this branch's
base when Z2 merged (PR #45, `34ea4cb6`), adding `tests/e2e/zoom-managed-join.spec.ts`. 11 + 1 = 12.
The same arithmetic explains gate 2: 291 files / 6781 tests against the branch's own local
266 / 6263. **CI therefore proved A9 against current `main` with Z2 included** — stronger evidence
than the branch head alone would have been.
