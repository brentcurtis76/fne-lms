## BLOCKING — a stale submission can overwrite a concurrent marketing opt-in

The route reads the existing lead, decides what to write, then writes. Between
that read and that write, another submission (or an admin action) can set
`marketing_opt_in = true`; a decision computed from the stale read then clobbers
it. This is a **consent regression** — the person opted in and the record says
they did not — so it matters more than the ordinary lost-update case.

Fix it so the write cannot depend on the stale read:
- **Never write the marketing columns on the update path unless this submission
  is itself opting in** (`marketingOptIn === true`, with fresh evidence). An
  absent or false checkbox writes nothing at all — not `false`, not NULL.
  Opting out is unsubscribe's job, never a form omission.
- If any code path still needs to clear them, it must be conditional in the
  statement itself (e.g. a guarded UPDATE), not decided in application memory
  from an earlier SELECT.
- Test the race explicitly: simulate the interleaving (read returns
  `marketing_opt_in: false`, the write is issued after a concurrent true) and
  assert the update payload contains **no** marketing keys, so a stale
  submission is structurally incapable of clearing the flag.
