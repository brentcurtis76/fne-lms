## B1 residue — decimal-dot prices bypass the scanner

Confirmed independently by the PM against `scanText`:

```
MISSED   "Programa: 2500.00 euros por persona"
MISSED   "2,500.00 euros"
MISSED   "EUR 2,500.00"
MISSED   "euros 2500.00"
CAUGHT   "2.500,00 euros"
CAUGHT   "Programa: 2500 euros"
```

Sol also confirmed the first of these survives into
`.next/static/chunks/pages/pasantias-*.js` on a real production build while the
scanner exits 0.

`wholeAmountPattern` (line ~166) is:

```js
`(?<!\\d)(?<![\\d][.,])(?:${patterns.join('|')})(?:,\\d{2})?(?!\\d)(?![.,]\\d)`
```

The decimal tail admits a comma only. **Note the trap before you edit:** the
trailing `(?![.,]\\d)` is not incidental — it is the false-positive control that
keeps `€12.500` and `€2.5000` from firing, added after Sol's round-1 S1, and it
is the same clause that rejects a dot-decimal tail. A fix that widens the tail
without preserving that control will bring back the crying-wolf failure the
comment above the function warns about.

### Preferred approach

This guard has now been wrong three times in three different ways: unbounded
amounts (r1 S1), missing currency words (r3 B1), and now the decimal separator.
Each fix has been one more alternation. **Prefer a fix that ends the class
rather than adding a fourth special case** — for example, normalising a digit
run to a canonical form before matching, so `2500`, `2.500`, `2,500`, `2500.00`,
`2,500.00` and `2.500,00` all collapse to the same thing and the pattern has one
shape to recognise instead of six.

If after trying it you judge normalisation to be worse here — because it
loses the boundary information the false-positive controls depend on, or makes
the minified-bundle windows unworkable — then extend the tail to
`(?:[.,]\\d{2})?` instead, and **say plainly in your report that you chose the
narrower fix and why**. Either is acceptable. Silently adding one more
alternation without addressing the pattern is not.
