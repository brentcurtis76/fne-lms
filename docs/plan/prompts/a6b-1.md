## CONTEXT YOU NEED

### 1. The API contract you are posting to — read it, do not re-derive it

`POST /api/pasantias/lead`, JSON body. Field names are **exactly** these
(`lib/pasantias/leads.ts:79` `LeadSubmissionBody`):

| body field | required | notes |
|---|---|---|
| `cohort` | **yes** | must equal `COHORT_ID` from `lib/pasantias/cohort-public.ts` (`'octubre-2026'`). Import the constant — never type the string. A wrong/absent value is a 400 with `fields.cohort`. |
| `firstName` | **yes** | max 80 |
| `lastName` | **yes** | max 80 |
| `email` | **yes** | max 140, format-checked server side |
| `institution` | **yes** | max 140 |
| `phone` | no | max 40 |
| `roleTitle` | no | max 140 |
| `numPeople` | no | integer 1–60 (`LEAD_NUM_PEOPLE_MIN`/`MAX`); anything else → 400 `fields.numPeople` |
| `message` | no | max 1000 |
| `consent` | **yes** | must be **strictly boolean `true`**. Not `'on'`, not `'true'`, not `1`. |
| `marketingOptIn` | no | boolean; **defaults false, must ship unchecked** |
| `sourcePath` | no | browser-reported path. Send `window.location.pathname` (+ search is fine only if it still starts with `/`). Never contributes an error — a value the server refuses is silently dropped to null. |
| `utmSource` / `utmMedium` / `utmCampaign` | no | max 140 each, read from the URL query (`utm_source`, `utm_medium`, `utm_campaign`) |
| `website` | — | **honeypot**. Ship it as a hidden/off-screen input. If it is non-empty the server returns a normal-looking `200 {success:true}` and stores nothing. |

Responses:
- `200 {success: true}` — success. **Identical for a first-time lead and a
  resubmission of a known address** (anti-enumeration) and identical for the
  honeypot. Your success panel must therefore never claim anything address-specific.
- `400 {error: 'Revisa los datos del formulario.', fields: {<bodyField>: '<es-CL message>'}}`
  — per-field errors, keyed by the body field name above.
- `429` — rate limited (5/min per IP). Body from `lib/rateLimit.ts`.
- `500 {error: 'Error al guardar la solicitud'}` / `{error: 'Error al procesar la solicitud'}`
- `503 {error: 'Formulario temporalmente no disponible'}` — table missing.

The es-CL error strings are already written and exported — **import them, do not
retype them**: `LEAD_VALIDATION_MESSAGES` in `lib/pasantias/leads.ts:134`
(`firstNameRequired`, `lastNameRequired`, `emailRequired`, `emailInvalid`,
`institutionRequired`, `consentRequired`, `cohortInvalid`, `numPeopleInvalid`,
`tooLong(max)`), and `LEAD_FIELD_LIMITS` / `LEAD_NUM_PEOPLE_MIN` /
`LEAD_NUM_PEOPLE_MAX` at `:62`/`:75`. Client-side validation must produce the
**same message for the same problem** as the server, so a client-caught error and
a server-caught one read identically.

## ACCEPTANCE CRITERIA — each independently verifiable

- **[A1] Fields + split consent.** Form posts every field in §1 with those exact
  names. Two visually and semantically separate checkboxes: required processing
  consent with `data-testid="pasantias-consent"` and optional, **unchecked**
  marketing opt-in with `data-testid="pasantias-marketing-optin"`. The processing
  label renders `PRIVACY_POLICY_LINK_LABEL` as a link to `PRIVACY_POLICY_PATH`,
  derived from the constants. Honeypot `website` present and hidden from sighted
  and assistive users alike (`aria-hidden` + `tabIndex={-1}` + off-screen, not
  `display:none` on a focusable control). `consent` is sent as boolean `true`,
  never a string. UTM params and `sourcePath` captured from the browser.
- **[A2] Optionality is proven.** A submission with the marketing box untouched
  succeeds and sends `marketingOptIn: false` (or omits it) — asserted at **both**
  unit and e2e level. A submission with it checked sends `true`. Nothing in the UI
  couples the two boxes.
- **[A3] Client validation + focus.** Submitting with empty required fields does
  **not** hit the network; it renders per-field errors using the imported
  `LEAD_VALIDATION_MESSAGES` strings and moves focus to the **first invalid
  control** in DOM order. Errors are associated with their inputs
  (`aria-invalid` + `aria-describedby` pointing at the message element).
- **[A4] Pending, success, error.** While in flight the submit control is disabled
  and reads as busy (`aria-busy` or an explicit pending label — es-CL). On `200`
  the form is replaced by (or accompanied by) a success panel with
  `role="status"`, containing a link to the brochure (`/api/pasantias/brochure`)
  and a note that the programme is also on its way by email. On a `400` with
  `fields`, those server messages render per-field. On `429`/`500`/`503` or a
  network throw, a generic es-CL error renders **and every value the person typed
  is still in the form** — nothing is cleared, ever.
- **[A5] Keyboard + a11y.** The whole form is completable with keyboard only:
  every control reachable by Tab in visual order, both checkboxes toggleable with
  Space, submit reachable and activatable. Every input has an associated
  `<label>` (`htmlFor`/`id`, not placeholder-as-label). Every interactive element
  carries a `data-testid`. axe reports **no serious or critical violations** on
  `/pasantias` with the form present — the existing axe spec at
  `tests/e2e/pasantias-page.spec.ts:417` covers the page and must stay green.
- **[A6] The guard stays green and honest.** `npx vitest run
  __tests__/pages/pasantias-hardcoded-cohort.test.ts` passes. If any declaration
  count changed, its `reason` prose names the new site with file and line, in the
  existing style. If none changed, say so in the report and say why (i.e. your
  copy contains no module value).
- **[A7] Page contract intact.** `id="programa"`, `data-testid="pasantias-programa"`,
  `aria-labelledby="programa-title"`, `pasantias-cta-programa` (the hero anchor),
  `pasantias-cta-ficha` and `pasantias-cta-whatsapp` all still work. One `h1` and
  valid heading order across the whole document including `Footer` — the form must
  not introduce a heading that breaks the sequence.
- **[A8] No price, no commercial import.** No currency symbol, amount, or price
