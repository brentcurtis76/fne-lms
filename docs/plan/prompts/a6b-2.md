## FINDING 1 (BLOCKING) — an invisible field can silently kill a real lead

`components/pasantias/LeadForm.tsx` reads `utm_source` / `utm_medium` / `utm_campaign`
from the query string on mount and copies them **raw** into the request body. It then
calls `validateLeadSubmission` on that body before any `fetch`.

`LEAD_FIELD_LIMITS.utm` is 140. A longer value produces `errors.utmSource` — and:

- there is no input, no label and no error element for `utmSource`, so nothing renders;
- `FOCUS_ORDER` is `[...TEXT_FIELDS, 'consent']`, so `focusFirstInvalid` finds nothing to
  focus;
- `handleSubmit` returns early on `!result.ok`.

Net effect: a visitor fills the form correctly, presses the button, and **nothing happens
at all.** No request, no message, no focus change. The lead is lost and neither the
visitor nor FNE ever knows. Sol reproduced it against a production build with a
141-character `utm_source`: zero POSTs, zero visible errors, no focused element. The PM
reproduced the contract half of it — an otherwise-perfect body with a 141-character
`utmSource` returns `ok: false` with exactly one error key, `utmSource`.

**The principle that settles how to fix it is already ratified in this project.** A5
faced the same question for `source_path` and chose to DROP an unusable value to null
rather than reject the submission, and the LEDGER records why (2026-08-04, A5 r2): nobody
*types* these fields, so an error against them reaches a form with nowhere to render it —
*"losing one lead's attribution is the cheap failure; losing the lead is not."* That is
why `sanitizeSourcePath` never contributes an error and why `LEAD_VALIDATION_MESSAGES` has
no `sourcePath` entry.

Apply the same rule client-side to the three UTM values: **an unusable UTM value is
dropped, never a reason to refuse the submission.** Over the cap is unusable. Do not
truncate — a truncated campaign name is a wrong attribution recorded as if it were right,
and the ratified precedent drops rather than mangles.

**Do not fix this by editing `lib/pasantias/leads.ts`.** It is a frozen A5 file. See OUT
OF SCOPE.

## FINDING 2 (BLOCKING, found by the PM while verifying Sol's) — UTM is one instance of a class

The real defect is not the UTM fields. It is that **the component can enter a state where
it holds errors it cannot show.** Any validation key with no rendered control does it.
Enumerate `LEAD_VALIDATION_MESSAGES` against the form's controls and there is a second one
already reachable today: **`cohort`.**

`errors.cohort` cannot come from the client path (the component imports `COHORT_ID`, so
it always agrees with itself) — but it can arrive from the **server**, and the validator's
own comment says exactly when: *"a stale cached form or a hand-crafted POST cannot file a
lead against a cohort that is not running"* (`lib/pasantias/leads.ts`). A visitor holding
a cached page from a retired cohort passes client validation against the stale constant,
posts, and the route answers `400 {fields: {cohort: …}}`. The component's 400 branch does
`setErrors(payload.fields)` and `focusFirstInvalid(...)` — and renders nothing, focuses
nothing, shows no form-level error. **The same dead form, on the path the plan explicitly
anticipated.**

So r2 owes a structural fix, not a second special case:

**No error may ever be invisible.** After errors are set — from client validation or from
a 400 — if any error key has no rendered control to attach to, the form must also show
the form-level error so the visitor is never left with a button that does nothing. And a
test must enumerate every key the validator can produce against the form's rendered
controls, so a field added to `LEAD_VALIDATION_MESSAGES` in a future phase cannot
reintroduce this class silently.

## FINDING 3 (SHOULD-FIX, Sol S1) — the generic error is only generic by luck

`components/pasantias/LeadForm.tsx:288` renders `payload.error || GENERIC_ERROR` for
429/500/503. Every string that route currently returns is es-CL and PII-free, so nothing
is wrong today — which is exactly Sol's point: the contract says the component owns the
message for those statuses, and rendering the server's string makes that property
accidental. A future route change can put English or implementation detail on the page.

**Reserve the server payload for the 400 field path. Every other failure — 429, 500, 503,
an unparseable body, a network throw — renders `GENERIC_ERROR`.**
