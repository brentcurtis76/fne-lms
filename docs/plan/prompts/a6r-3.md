## B1 — the hardcoding guard is bypassable (blocking)

`__tests__/pages/pasantias-hardcoded-cohort.test.ts:55` scans the page source against a
**hand-maintained list of strings** with `source.includes()`. It therefore misses:

- numeric and boolean facts — `{COHORT_VISIT_DAY_COUNT}` replaced by a literal `9` passes
- formatted or derived dates
- **any new field added to the module later** — silently uncovered
- trivial composition: `['Escola', 'Virolai'].join(' ')` defeats a substring check
- values under 12 characters, excluded by design, so `Codocencia` and `Cenas` are unchecked

**This is the third time on this project that a hand-enumerated guard has been found
incomplete** — the leak scanner's separator list was wrong three times, by three
different authors, before it was fixed by deriving the set instead of listing it. Do the
same here.

**Derive the cases recursively from `COHORT_PUBLIC`** so every primitive leaf — string,
number, boolean, date — is covered automatically and a new field cannot escape by being
forgotten. Assert the count of derived leaves so a structural change is visible.

A substring scan can't catch composition, so pair it with a **render contract**: for
each leaf, prove the rendered page contains the module's value and changes when the
module changes. The PM has already shown the mechanism works by mutating a school
highlight and watching it render; the question this round must answer is whether a
*regression* would be caught. Prove it: mutate at least one string, one number and one
short value, and show a named failure for each.

Keep documented limits documented — if something genuinely cannot be covered, pin it as
an explicit expected-gap with the reason, not as silence.

## B2 — the runtime image probe is not deployment-safe (blocking)

`pages/pasantias.tsx:198` resolves four photo slots and eight portraits with **37
`existsSync` probes per request** against `public/`.

PM-verified: the clean build's `.next/server/pages/pasantias.js.nft.json` traces **14
files, zero under `public/`, zero images**, and `next.config.js` sets no
`outputFileTracingIncludes`. Vercel bundles function runtime files from that trace and
serves `public/` separately, so these probes can resolve **every slot and portrait as
missing in production** — a page that renders correctly here and photo-less when
deployed. `ogImageUrl` (line 229) then falls back to a skyline file the same probe
called missing, producing a broken social preview.

I have **not** proved the production failure — it depends on Vercel builder behaviour I
can't exercise locally. That doesn't matter to the fix: **resolve image availability at
build time, not per request.** A generated manifest, a static import map, or an explicit
`outputFileTracingIncludes` plus a single memoised probe are all acceptable. A
per-request filesystem probe for static assets is the wrong shape regardless of whether
this particular platform happens to tolerate it, and 37 syscalls per request is a real
cost for a value that changes only when someone adds a file.

Whatever you choose, the **OG image must be independently guaranteed** — either it
provably exists, or the tag is omitted. A social preview pointing at a 404 is worse than
no tag.

## B3 — the hero eyebrow fails WCAG AA (blocking)

`#FBBF24` at 11px over the hero photograph measures **~3.10:1 at 390px and ~3.49:1 at
1440px**; 11px text needs 4.5:1. axe classifies photograph-backed text as `incomplete`,
so the serious/critical gate cannot catch it — that gate passing is not evidence here.

**The root cause is the veil, and it is a brand deviation, not just a colour choice.**
`pages/pasantias.tsx:560` renders
`from-brand_primary/[0.45] via-brand_primary/[0.55] to-brand_primary/80` — **45%
opacity at the top, exactly where the eyebrow sits.** The FNE brand manual's canonical
photo treatment specifies the veil **reaches 85% under the text** and dissolves before
the photo's centre of interest. The implementation is weaker than the brand requires,
and the contrast failure follows from that.

Prefer fixing the veil to the manual's specification over changing the text colour: it
addresses the cause, it is what the brand says, and it will fix the ratio without giving
up the yellow eyebrow the design intends. If after implementing it the ratio still falls
short, then take Sol's white-eyebrow option (measured ≥5.18:1) and say why.

**Add deterministic coverage for photo-backed text** — a test that samples the actual
rendered pixels behind the eyebrow and asserts the ratio, so this cannot regress into
the `incomplete` bucket again. State every measured ratio you introduce.
