## ITEM 1 — the PATCH is read-then-write, and two admins can breach D-03

**File:** `pages/api/admin/pasantia-leads/index.ts`, `handlePatch`.

Today the route reads the lead's status, validates the move with `canTransitionLead` against
that **snapshot**, then issues the UPDATE filtered on `id` alone:

```ts
const { data: current } = await supabase.from(TABLE).select('id, status').eq('id', id).maybeSingle();
// ... canTransitionLead(current.status, next) ...
await supabase.from(TABLE).update(update).eq('id', id).select(LEAD_COLUMNS).maybeSingle();
```

Nothing holds the row between those two statements. Two admin sessions on one `contacted` lead:

1. A reads `contacted`, B reads `contacted`.
2. B commits `contacted → converted`. Legal.
3. A, still validated against the stale `contacted`, commits `dismissed`.

The table now went **`converted → dismissed`**, and D-03 gives `converted` **zero outgoing
edges** — it is terminal. The API boundary is the *only* place that invariant is enforced
(D-04: the table's CHECK constrains the set of statuses, never the moves), so this is the one
guard, and it can be walked past.

**Fix — make the UPDATE's predicate carry the precondition**, so PostgreSQL evaluates it against
the row it has locked rather than against something the route read earlier:

```ts
.update(update).eq('id', id).eq('status', current.status)
```

Two consequences you must handle rather than leave implicit:

- **The `maybeSingle()` result becomes meaningfully empty.** Today a null there is unreachable;
  with the guard it means *somebody moved this lead between our read and our write*. Answer
  **409** with an es-CL message telling the admin the lead changed and to reload — do **not**
  retry, and do **not** fall through to a 200 with a null body. Include the current status in
  the body, matching the shape D-07 uses elsewhere in this plan for a 409.
- **A notes-only PATCH must keep working.** When the body carries no `status`, `current.status`
  is still the right guard value and the write must still succeed — do not accidentally make
  notes-only edits fail. Test this explicitly.

**Use `.eq()`, not an `.or()` filter.** Decision Log 2026-08-03 is binding: PostgREST accepts
`or=()` on SELECT but **rejects it on UPDATE** for non-PK columns, so an `or`-shaped guard
passes every mocked test and fails only in production — this repo has already paid for that
once (`lib/bots/store.ts:claimSessionTransition`). `.eq` on UPDATE is the proven form, and it is
exactly what A5's `claimAutoReplyWindow` uses for the same kind of atomic claim.

**Tests** (in `__tests__/api/admin/pasantia-leads.test.ts`):
- the UPDATE carries **both** filters — assert `updates[0].filters` equals `{ id, status }`;
- a concurrent move (the fake returns zero rows from the update) answers **409**, not 200/500;
- a notes-only PATCH still succeeds and still carries the status guard;
- the existing allowed-transition and denied-transition tests still pass unchanged.

## ITEM 2 — `sourcePathRepeatsUtm` can never fire for a multi-word UTM value

**File:** `components/admin/PasantiaLeadCard.tsx`.

```ts
return [lead.utm_source, lead.utm_medium, lead.utm_campaign].some(
  (value) => Boolean(value) && path.includes(value as string)
);
```

This is not merely imprecise — for a whole class of values it is **dead code**. The stored
`utm_*` columns hold **decoded** values (`pasantias e2e`), while `source_path` holds the raw
query string where that same value is **percent-encoded** (`pasantias%20e2e`). And
`sanitizeSourcePath` (frozen, `lib/pasantias/leads.ts`) **refuses any stored path containing
whitespace**, so the decoded form can never appear there. `path.includes(value)` therefore
cannot match any UTM value with a space in it, ever. [A-new-2]'s banner — the one that tells the
admin the two fields are one observation written twice — silently never renders for those leads.

The same expression has a second, opposite bug: a short or common value (`utm_source=pasantias`
against `/pasantias`) matches incidentally and claims a repeat that is not one.

**Fix: compare properly instead of by substring.** Parse the stored path's query string with
`URLSearchParams` and compare **per key** — `utm_source` against the query's `utm_source`, and
so on — on decoded values. That kills both bugs at once: the encoding mismatch disappears
because both sides are decoded, and the incidental-substring class disappears because you are
comparing whole values under the right key rather than scanning the whole path.

Notes on doing it safely:
- `source_path` may be any stored string. It is a path, not an absolute URL, so build the params
  from the substring after the first `?` rather than handing the whole thing to `new URL()`.
  A path with no `?` has no params and must return `false`, not throw.
- Keep the function exported and pure — the existing tests render through it and Sol reviewed it
  as the [A-new-2] surface.
- The banner copy does not change.

**Tests** (in `__tests__/components/admin/pasantia-lead-card.test.tsx`):
- a **multi-word** UTM value that is genuinely repeated (`utm_campaign=pasantias e2e` stored
  decoded, `source_path=/pasantias?utm_campaign=pasantias%20e2e`) → banner **shows**. This is the
  case that is broken today; write it first and watch it fail before the fix;
- `+`-encoded spaces as well as `%20`, since both appear in real query strings;
- an incidental substring (`utm_source=pasantias`, `source_path=/pasantias` with no query) →
  banner **does not** show;
- a genuinely independent UTM (path carries a different value under that key) → no banner;
- `source_path` null, and `source_path` with no `?` → no banner, no throw.

## ITEM 3 — the terminal-state card has a label pointing at nothing

**File:** `components/admin/PasantiaLeadCard.tsx`, the "Cambiar estado" block.

When `transitions.length === 0` (a `converted` lead) the `<select id={dom('lead-status')}>` is
replaced by a `<div>` — but the `<label htmlFor={dom('lead-status')}>` above it still renders,
now pointing at an id that does not exist in the document. A screen reader announces a label for
a control that is not there, and r2's own guard ("every `label.htmlFor` resolves to exactly one
element") passes only because it never renders a terminal lead.

**Fix:** in the terminal branch, do not emit a `<label htmlFor>` — render the caption as a plain
element (a `<div>` with the same classes is fine), or move the label inside the non-terminal
branch. Either is acceptable; say which you chose.

**Test:** extend r2's `htmlFor`-resolution assertion so it also covers a **`converted`** lead —
that is precisely the case it currently cannot see. Every rendered `label[for]` must resolve to
exactly one element, for a lead in each of the four statuses.
