## Non-negotiables learned from A2 (do not re-derive them the hard way)

1. **Grant-list form, not a denylist.** For every one of the five tables:
   `REVOKE ALL ON <t> FROM anon;`
   `REVOKE ALL ON <t> FROM authenticated;`
   `GRANT SELECT ON <t> TO authenticated;`
   An allowlist cannot leak a privilege that does not exist yet — this is how
   PostgreSQL 17's `MAINTAIN` slipped past A2's first two attempts. Sol bound
   B3 to this form explicitly.
2. **RLS is not the write boundary.** TRUNCATE/REFERENCES/TRIGGER are GRANT-level
   and RLS never sees them; Supabase's default privileges hand them to
   anon/authenticated on every new table. The REVOKEs above are what actually
   close it.
3. **pgTAP must assert privileges AND policies.** Pin the exact grant set from
   the real ACL — `aclexplode(pg_class.relacl)` — not `information_schema`,
   which hides PG-specific privileges (that blindness is exactly how the
   MAINTAIN gap survived). Add version-guarded MAINTAIN asserts
   (`current_setting('server_version_num')::int >= 170000`, else `skip`):
   **local and CI run PostgreSQL 17.6, production runs 15.8**, so both branches
   execute somewhere.
4. Additive only; no DROP/TRUNCATE/destructive ALTER anywhere, including the
   rollback section, which must be forward-only. Model the file on
   `supabase/migrations/20260731140500_add_pasantias_leads.sql` (header access
   matrix + table/column comments) and the suite on
   `supabase/tests/030-pasantias-leads-rls.sql`.

## Design points worth stating in the migration's comments

- `email_campaign_sends.provider_batch_key` is **created unused** — B2's findings
  §1.4.4 showed every non-status-quo idempotency option needs it, and a nullable
  column is free now versus a migration later. B10a decides the mechanism.
- `email_webhook_events.detail` is a **sanitized, PII-free** projection (D-06):
  it must never carry `to`/`cc`/`bcc`/subject/html. B4b's `process_webhook_event`
  does the allowlisting; B3 only creates the column and documents the rule.
- `email_contacts` anonymization contract (D-06): `anonymized_at` marker + the
  two-shape identity CHECK (normal row with consistent normalized email, or
  anonymized row with NULL identity). Erasure is anonymize-only — hence
  `email_campaign_sends`' FK is `ON DELETE RESTRICT`, and `email_suppression`
  tombstones must survive erasure.
- Consent/basis columns are NOT NULL **without defaults** (D-12): a default
  would let the database manufacture a legal basis.
