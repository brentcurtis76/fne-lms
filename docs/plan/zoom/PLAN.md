## 1. Executive verdict

The original plan had the right architectural spine (Meeting SDK embed + S2S OAuth REST + webhooks + desired-state convergence + fake adapter + spikes-first) but four disqualifying flaws, all confirmed by code/doc evidence:

1. **It wrote Zoom's raw `join_url` (passcode-embedded — verified secret-equivalent) into `consultor_sessions.meeting_link`**, a column served by `select('*')` APIs, iCal, and reminders to any growth-community member — making the "authorized join endpoint" security theater. Worse, the **existing** session-detail API already leaks facilitator-only reports and attendee emails to any GC member; that ships broken today and must be fixed first.
2. **It treated Vercel crons as a queue.** Verified: crons can overlap, never retry, and can silently miss or double-fire. Every pipeline stage needs atomic lease-based claims.
3. **Privacy was sequenced last.** Ley 21.719 takes effect 2026-12-01, inside the delivery window; educators can name identifiable students in transcripts, and the project rule bans student PII in AI prompts. The plan enforces this in-product: consent-gated recording and automated sanitization before any text reaches an LLM. (An external legal-review gate existed in v2.1 and was removed by owner decision 2026-07-28 — §12.)
4. **It let Zoom data drift toward billing.** New non-negotiable: discounted contract hours = planned/approved duration, always; Zoom durations are comparison/audit only; only an admin, with a reason, through an append-only override, may change billable hours.

The revised plan keeps the spine, adds a trust boundary with a single authorized opening, splits schemas public/private, makes every job durable, moves governance to Z0, and adds the timezone and hours invariants as tested contracts. Effort is honestly re-estimated at **≈82–114 padded agent-days (~15–20 focused Claude Code days) + ~1–2 weeks of human/field work (account setup, school tests, Mora's evaluation)**, with a calendar range (§15) that tightens only after the Z0 spikes.

## 4. Final architecture

**Components** (all following existing repo patterns — `lib/api-auth.ts` auth, service-role writes, hand-rolled Tailwind es-CL UI):

- **Integration layer** (`lib/zoom/`): S2S token provider (DB-cached, single-flight); REST client (typed errors, 429 `Retry-After`, read-back of effective settings); SDK JWT signer (pure function; claims `appKey, mn, role, iat, exp, tokenExp`, exp=tokenExp=iat+2h); webhook verifier (HMAC over raw body + timestamp freshness + CRC responder); `ZoomApi` interface + in-memory fake (`ZOOM_MODE=mock`), DI seam per `lib/bots/types.ts`.
- **Data**: private `zoom_internal` schema (tokens, hosts, meetings w/ secrets, webhook events, jobs, recording files, raw transcripts) + public projection/business tables (`session_meetings_public`, `zoom_attendance`, `session_recordings`, `session_transcripts` metadata, `ai_minutas`, `session_hour_overrides`) — §6/§7.
- **Jobs**: one durable queue (`zoom_internal.zoom_jobs`, lease-claimed via SECURITY DEFINER RPC), one per-minute cron ticker + hourly reconcile; staged idempotent pipelines for provisioning, recording transfer, transcription, minuta generation, retention.
- **Join surface**: `/meet/session/[id]` + `/meet/community/[id]` pages (SSR-gated) + `POST /api/meet/.../join` — the single boundary opening returning SDK payload or (link-out mode) the raw URL, per-persona authorization in §5.
- **Post-session**: attendance ingestion (webhooks + report reconciliation) → comparison-only hours panel + admin override; recording→storage→transcript(auto-sanitized)→AI minuta→approval chain→seguimiento dashboard.
- **Notifications**: existing `notificationService` events (fire the declared-but-never-fired `session_created/rescheduled/cancelled`) + Resend email with platform links only.

**Data flow (happy path)**: admin approves session → `meeting_provision` job creates Zoom meeting under facilitator's licensed host (`America/Santiago` wall-clock + timezone) → `session_meetings_public` row appears (UI badge) → participants join via `/meet/...` (SDK, license-free, `customerKey`=UUID-sans-hyphens) → webhooks record attendance → meeting ends → reconcile pulls participant report → recording.completed → transfer job streams to Supabase (S3 multipart) → verify → Zoom trash → transcribe (Opus-transcoded, es) → transcript auto-sanitized (attendee-allowlist + NER → `sanitized_text`) → minuta job → consultant reviews → admin approves+publishes → report + cuadrante + dashboard.

## 5. Trust boundaries and authorization model

**Boundary**: everything Zoom-credential-shaped lives server-side (`zoom_internal.*`, env vars, route memory). Exactly one narrow per-request opening: the authorized join payload from `POST /api/meet/{surface}/{id}/join`. No page props, supabase-js query, email, iCal, or cron payload ever carries a Zoom secret.

**Secrets inventory** (full table in security design; highlights): S2S credentials/tokens, SDK client secret, webhook secret — env/`zoom_internal` only, reachable by nobody. SDK JWT — minted per request, never persisted, `role` decided server-side (client-supplied role ignored). `mn`+plaintext passcode — only inside authorized join payloads (verified: web SDK requires the plaintext passcode; the encrypted `pwd` token is undocumented for SDK join). `join_url` — never sent in SDK mode; in link-out mode returned only by the join endpoint to the same authorized personas. ZAK (host credential, 2h) — fetched at start-click (`user:read:token:admin` scope), never persisted; `start_url` — never used or stored (re-fetch via Get Meeting if ever needed). Recording `download_token` — job-only, nulled after transfer. Raw transcripts — `zoom_internal`, dedicated endpoint only.

**Join authorization (consultor sessions — join list = `session_attendees(expected)` ∪ `session_facilitators` ∪ admins; viewing ≠ sitting in):**

| Persona | Result |
|---|---|
| Admin | 200, host-capable (`role:1` + ZAK when starting) |
| Assigned facilitator | 200, host (`role:1` + fresh ZAK for their mapped licensed host) |
| Expected attendee | 200, participant (`role:0`, mn+passcode, profile display name, customerKey) |
| Active GC member NOT in attendees | **403** es-CL: "No estás en la lista de asistentes de esta sesión…" — live audio is raw session content; attendees list feeds attendance/hours; remedy = facilitator adds them (one click) |
| Same-school non-facilitator consultor | **403** — PROJECT_STATE: *el asesor nunca lee contenido crudo de sesiones ajenas* |
| Other-school user | **404**, byte-identical to nonexistent UUID (no existence oracle) |
| Anonymous | 401 (API) / `redirect /login?next=/meet/session/{id}` (page) |
| Cancelled/ended meeting | **410** for every persona incl. admin |

**Community meetings**: join list = active membership in the meeting's community (`user_roles.community_id`, `is_active`) + admins + the school's assigned consultants; everyone joins `role:0` (Zoom-host powers stay with FNE identities); `join_before_host:true`. Non-member 403; other-school 404.

## 6. Public/private schema proposal

**`zoom_internal` (new schema, migration-created). Access mechanics (v2.1 correction)**: supabase-js can only address a schema that is in the project's PostgREST **exposed schemas** list — the service-role key bypasses RLS but does not make an unexposed schema addressable. Decision: **expose `zoom_internal` in the Data API config, and deny everything by grants** — `REVOKE ALL` from `public/anon/authenticated` on schema + tables + sequences + default privileges; `GRANT USAGE/ALL` to `service_role` only; RLS enabled with zero policies as belt-and-braces. Application code uses `serviceClient.schema('zoom_internal')`. pgTAP `002-zoom-internal-isolation.sql` proves anon/authenticated denial (`has_schema_privilege` = false, zero `role_table_grants` rows); one e2e-mock spec additionally asserts an authenticated PostgREST request to a `zoom_internal` table returns an error, not data. Ops checklist: verify `zoom_internal` IS in the exposed list (needed for the service client) and that the grants tests are green — the grants, not the exposure list, are the enforcing control. Tables:
`zoom_token_cache` (single row) · `zoom_hosts` (licensed only: zoom_user_id, email, profile_id mapping, is_active, max_concurrent default 1) · `zoom_meetings` (surface_type+surface_id unique, **school_id NOT NULL**, mn, uuid, host, **plaintext passcode**, **join_url**, effective_settings jsonb read-back, status machine pending→provisioned→started→ended/cancelled/deleted/error, starts_at/duration) · `zoom_webhook_events` (dedupe_key = sha256(raw body) UNIQUE, raw_payload nulled at 30d) · `zoom_recording_files` (zoom file id unique, download token nulled post-transfer, transfer_status pending→transferring→stored→verified→zoom_trashed→zoom_deleted/failed) · `zoom_transcripts` (**raw text isolated here — access-restricted, never in prompts**, surface+school_id, unique per surface; v2.2: + `sanitized_text` (the ONLY column any LLM prompt may read) + **`sanitization_status` state machine: `pending` → sanitizer runs → `sanitized` (density heuristic below threshold; minuta may proceed) | `flagged` (above threshold; **BLOCKS minuta generation** until a human confirms/edits via PUT on the transcript endpoint → `reviewed`, which unblocks)** + `sanitizer_version` (re-running a newer sanitizer recomputes status and may re-flag) + `reviewed_by/reviewed_at` (set on the flagged→reviewed transition)) · `zoom_jobs` (§ durable queue).

## 9. Host / license / concurrency model

**Inventory** (synced by `host_sync` job from `GET /users`, verified license fields): only **Licensed** users enter `zoom_internal.zoom_hosts` — **Basic users are excluded entirely** (verified: cloud recording requires a Licensed host on Pro/Business/Enterprise; recordings are core, so the v1 "Basic hosts for ≤35-min meetings" idea is dead). Rows: consultant-mapped hosts (`profile_id` set) and org pool hosts (`profile_id` null, e.g. `reuniones1@fne`). Admins who lack their own Zoom license start meetings via pool-host ZAKs.

**ZAK / role-1 issuance rule** (precise; no blanket impersonation; v2.1-tightened): `role:1` + ZAK issued only to (a) the **assigned facilitator**, and only for **their own** mapped host identity (`profile_id = facilitator` AND that host is the meeting's `host_zoom_user_id`); (b) **admins**, but only for **organization-controlled pool identities** (`profile_id IS NULL`) or explicitly FNE-owned accounts flagged `org_owned=true` — an admin never receives a consultant's personal ZAK. Every issuance writes a `zak_issued` audit event. Other consultants — even same-school — never receive host credentials. If a meeting is hosted on a consultant's personal identity and that consultant is absent, an admin's path is host-reassignment to a pool identity (re-provision job), not impersonation.

**Assignment**: consultor sessions prefer the lead facilitator's mapped host; fallback = least-loaded pool host. Community meetings always use pool hosts.

**Concurrency**: `EXCLUDE USING gist (host_zoom_user_id WITH =, tstzrange(starts_at - interval '15 min', ends_at + interval '45 min') WITH &&)` on active `zoom_meetings` rows — the insert IS the reservation (23P01 = busy → next candidate; no TOCTOU). The ±15/45-min buffer models early joins and overruns. Beyond the buffer: `meeting.started`/`ended` webhooks track reality; reconcile alerts when a host's live meeting collides with their next slot and auto-enqueues re-provision onto a free host — **platform links make host reassignment invisible to users** (new mn/passcode served by the same join endpoint; nothing user-held invalidates). Entitlements: Pro = 1 concurrent (verified; 2nd meeting also requires host/alt-host start on Business+); `max_concurrent` column exists but the DB constraint assumes 1 — upgrading to Business/Education (2 concurrent) is a documented migration (swap exclusion constraint for a count-check in the assignment RPC), classified deferred scope.
**Failure modes**: host disabled/license removed → `host_sync` marks inactive → reconcile re-provisions its future meetings onto other hosts + admin alert; no host free → job `failed:no_host_available` + health-panel alert (interactive scheduling gets a 409 with the conflict window); recording capacity = pooled 10GB/license (verified) — transfer job frees space within hours and reconcile alerts at 80%; recording continues past quota until meeting end (verified), so a full pool degrades gracefully.

## 11. Planned-hours, Zoom-comparison, and admin-override model

**Invariant**: the amount discounted from the contract = the **planned/approved duration**. Zoom execution data is comparison/audit only and can never automatically change contract hours, reservations, consumption, consultant payment, `contract_hours_ledger.hours`, or any aggregate. No webhook, reconcile job, consultant action, or AI process can reach the override path (it is admin-session-gated route code with no service-side caller).

**Seven quantities, distinguished and stored**:
1. *Planned/approved duration* — `scheduled_duration_minutes` (generated column) at approve time; the **current approved snapshot**: `contract_hours_ledger.planned_minutes_snapshot` (new additive column) written by `createReservation`, updated ONLY by the pre-execution reschedule rule — with an **append-only revision history** (each change writes a `session_activity_log` entry: old minutes, new minutes, actor, timestamp — written **inside the same transaction** as the snapshot/ledger update, v2.2.2), so every historical approved value remains reconstructible (v2.2.1 — resolves "immutable" vs "reschedule updates").
2. *Reserved contract hours* — existing `createReservation` behavior preserved (reserves from scheduled duration at approve).
3. *Zoom meeting elapsed* — `zoom_meetings` started/ended webhook instants (reconcile-corrected).
4. *Lead-facilitator presence* — summed `zoom_attendance` intervals for the lead facilitator (rejoin-deduped).
5. *Participant attendance* — per-person `zoom_attendance` totals.
6. *Final discounted/billable* — ledger `hours`; equals (2) unless an admin override exists.
7. *Cancellation penalties/returns* — existing devuelta/penalizada clause flow, **fully separate** from overrides.

**Recommended comparison metric**: **lead-facilitator presence (4)** — the consultant's billable presence — shown alongside meeting elapsed (3); both preserved for audit. Edge handling: join-before-host/early participants don't affect (4); reconnects merge intervals; overruns/no-shows/host-never-joined simply show as deltas; multiple facilitators → lead's presence is the metric, others displayed; partial outages → reconcile report is authoritative over webhooks.

**Reschedule rule**: admin-approved reschedule while `programada` (pre-execution) → reservation, snapshot, and revision entry update **in one service-role transaction (v2.2.2)**: ledger `hours` recomputation + `planned_minutes_snapshot` + the `session_activity_log` revision row commit or roll back together — a single RPC, because the existing activity-logging path is best-effort and may not fail the update on its own (this also fixes the verified existing gap where reschedules silently leave the ledger stale). Once execution begins (`en_progreso`+) or finalized: planned values frozen; changes only via override. **v2.1 sequencing: the snapshot column, approval-time snapshot write, atomic pre-execution reschedule+ledger update, and the planned-hours invariant tests land in Z1b/Z2 — before any managed session is provisioned** — so no session can ever exist without its approved-duration evidence. Only the comparison/override UI waits for Z7.

**Payment semantics (Brent, 2026-07-13)**: *what is booked is what the consultant is paid* — one ledger value drives both school contract consumption and consultant payment. Pre-execution booking edits adjust that value (the reschedule rule above). Post-execution, an override is at **admin discretion** (v2.2) with a **mandatory reason** and a useful `reason_category in ('consultant_shortfall','school_request','technical_failure','other')` — all categories audited and visible on the health panel. **Zoom data still never adjusts hours automatically** — the override RPC remains the only path and has no service-side caller. A single adjusted value flows to both consumption and payment — no separate payable field.

**Hours-consumer audit (v2.1, Z2 scope)**: every reader of session hours is inventoried and aligned to the ledger/planned-snapshot source of truth. Known offenders: `lib/services/school-hours-report.ts:200` and `pages/api/sessions/reports/analytics.ts:233,327` display `actual_duration_minutes` (which is verifiably only ever a copy of scheduled duration written at finalize) — both switch to ledger hours (with the override-adjusted value) or the planned snapshot, and `actual_duration_minutes` is deprecated (kept for compatibility, never displayed as "actual").

**Admin UI** (admin session detail + hour-ledger view): Planificado 60 min · Zoom (presencia facilitador) 45 min · Δ −15 min (−25%) · metric label · banner "Las horas descontadas siguen siendo las planificadas salvo ajuste manual" · mismatch highlight ≥15% (review flag only). Action **"Ajustar horas descontadas"** (admin-only): canonical input = **integer billable minutes** (ledger `hours` derived as `minutes/60`, one rounding rule, everywhere); mandatory reason (normalized non-blank) + reason_category; shows previous value, new value, admin, timestamp, reason; supports reversal without erasing history. **Zero-waiver allowed** (Brent decision), implemented **additively** (v2.1.1 — the existing `hours > 0` CHECK is never dropped or replaced): new nullable column `contract_hours_ledger.effective_minutes integer CHECK (effective_minutes >= 0)`. `hours` keeps its original reserved value and constraint untouched (it doubles as historical evidence); every consumer reads billable time as `coalesce(effective_minutes/60.0, hours)` (single helper, applied in the Z2 hours-consumer audit). Overrides write `effective_minutes` (0 permitted = full waiver, rendered "Sesión eximida"). **Reversal restores the reversed override's own `previous_minutes`** (v2.1.2): with a chain 60 → 45 → 30, reversing the second override returns the effective value to 45; only reversing the first override in a chain clears `effective_minutes` back to NULL (planned value governs again). The reversal RPC reads `previous_minutes` from the target event inside the transaction.

**Data integrity — DB-enforced, not aspirational (v2.1)**: new public table `session_hour_overrides` (school_id NOT NULL, session_id, ledger_id, previous_minutes, new_minutes, planned_minutes_snapshot, reason NOT NULL CHECK (btrim(reason) <> ''), reason_category, request_id UNIQUE, payload_hash, created_by, created_at, reverses_override_id nullable FK). Enforcement:
- **Append-only by trigger**: BEFORE UPDATE OR DELETE trigger raises — override rows are immutable at the database level, not by convention.
- **Reversal integrity**: the apply RPC permits reversal only of the **latest effective, unreversed** override for that ledger entry (checked inside the transaction; violations 409), and restores that event's `previous_minutes` — not NULL — unless it is the first override in the chain.
- **Cross-tenant validation**: the RPC verifies school_id ≡ across session, ledger entry, contract/allocation before writing; mismatch aborts.
- **Idempotency with tamper detection**: repeated `request_id` with identical `payload_hash` → 200 (no-op replay); same `request_id`, different payload → **409**.
- **Actor bound to the authenticated identity** (v2.1.1): the override RPC derives the actor from `auth.uid()` **inside the function** — it is called with the administrator's own authenticated Supabase context (`createPagesServerClient`), never the service-role client, so the actor cannot be supplied as a spoofable parameter. The function aborts when `auth.uid()` is null (which also closes the service-role/jobs path structurally) and verifies an active admin `user_roles` row for that uid before writing; `created_by := auth.uid()`.
- **One transactional RPC** (`SECURITY DEFINER`, EXECUTE granted to `authenticated` — authorization happens inside via the auth.uid() admin check — revoked from anon, pgTAP-asserted incl. a non-admin-authenticated rejection case) performs: insert override row + set ledger `effective_minutes` + `admin_override=true, admin_override_reason` — atomically.
- **Override × cancellation**: overrides are valid only against `consumida` entries (post-finalize). Cancellation clauses (`devuelta`/`penalizada`) remain a fully separate flow; a session cancelled after being overridden is impossible by state machine (completed sessions don't cancel), and the fully-failed-session case is handled either by cancellation (pre-finalize) or zero-waiver (post-finalize) — stated explicitly so no path is ambiguous.
Aggregates recompute from the ledger as today; each occurrence of a recurring series is independent (per-session ledger rows already are).

Therefore: **(gate G1, Z0A)** verify FNE's disclaimer entitlement — without custom text, the standard disclaimer evidences `recording` only, NOT `transcription`/`ai_processing`; **(gate G2, Z0B)** verify consent events are retrievable via API/portal export. **Until G1+G2 both pass: recording stays DISABLED in link-out mode** (consent capture can't be guaranteed on a shareable URL), **and in SDK mode any unidentified participant in a recorded meeting makes that recording ineligible for transfer** (trash + metadata-only audit). **After both gates pass**: the locked custom disclaimer (v1 text, all three scopes) + the participant's explicit click, retrieved through the verified reporting path, is valid evidence — stored with `evidence_source='zoom_disclaimer'`, `subject_user_id NULL`, identity = display name (+`zoom_participant_uuid`). Residual risk recorded: display-name-only identity for such rows.
- **Recording is consent-gated at provision time (v2.1.2 — fixes the disable-race)**: managed meetings are provisioned with `auto_recording:'none'`. Recording is enabled (single PATCH, **response read back and confirmed** before it counts) only once every expected participant has an `accepted` row — normally reached before the meeting starts, since pre-join capture happens ahead of credential issuance. If the meeting starts before full acceptance, that session simply stays unrecorded. There is no window in which recording runs ahead of consent.
- **Decline (any expected participant)**: the participant still joins; the session stays (or becomes) unrecorded — recording is never enabled for it. Facilitator notified: "Sesión sin grabación: un participante no consintió". FNE's need to record never overrides an individual refusal; the session itself is never blocked.
- **Late decline while recording is active** (e.g. a participant added mid-meeting): join credentials are **held**; the platform signals the facilitator to stop the recording and issues the credentials only after the stop is confirmed (recording-stopped webhook / recording status read-back). The exact stop mechanism (Zoom live-meeting control API vs facilitator SDK action + webhook confirmation) is verified in the **Z0B spike**.
- **Withdrawal (after the fact)**: `withdrawn` row triggers the deletion path — recording + raw/sanitized transcript purged by the retention job within 30 days, audited. The published minuta (human-approved business record derived from sanitized text) is retained; this boundary is stated in the notice text.
- **Notice version bump**: prior consents remain valid evidence for already-made recordings; new recordings require re-consent at the next pre-join under the new version.
- **Missing/incomplete consent at `recording.completed` (v2.2.1)**: if every participant maps to platform consent rows → transfer proceeds. If unidentified participants are present: transfer proceeds **only when gates G1+G2 have passed** (their disclaimer clicks are valid evidence); otherwise the recording is **ineligible for transfer** — trashed/deleted at Zoom, **metadata-only audit event** retained. Settings drift (disclaimer found off) always triggers the ineligible rule.
- **Host consent**: implicit in facilitating a session scheduled with recording (facilitators see the recording state at scheduling); still recorded as an `accepted` row at their own pre-join for evidentiary completeness.

**Consent & notices (Z0A deliverables, owner Brent — in-house, no external legal)**: notice v1 copy (es-CL, the three scopes, used by both the pre-join screen and the locked Zoom disclaimer); project-level **EIPD-lite** doc (`EIPD-ZOOM-2026-01`, agent-drafted, ~1h review); retention schedule with named business owner; access/deletion/incident-response procedures folded into the runbook. Retention/minimization: webhook payloads 30d; attendance emails 90d; recordings Zoom-side ≤7d post-verify then permanent; Supabase recordings 12mo from creation; raw transcripts 6mo post-publication **and (v2.1 hard ceiling) never longer than 12 months from creation regardless of publication or sanitization state** — a stalled/never-published transcript cannot live forever; same 12-month creation ceiling applies to recordings never attached to a published minuta; minutas = business records; tokens never persisted.

## 14. Feature flags and kill-switch behavior

Repo convention (`'true'` strings; client flags need explicit `FeatureFlags` entry + switch case in `lib/featureFlags.ts`):

- `FEATURE_ZOOM_MEETINGS` / `NEXT_PUBLIC_FEATURE_ZOOM_MEETINGS` — **master**. Server-enforced at: provisioning enqueue (approve hooks, community attach endpoint), join API, `/meet` SSR, signature minting. **When flipped off**: no new provisioning; join/signature routes return 503 es-CL ("Las videollamadas están temporalmente deshabilitadas"); **webhooks continue to be accepted** (idempotency ledger keeps filling — history preserved); recording-transfer, retention, and reconcile jobs **continue** (data already in flight must land safely and Zoom-side deletion must not stall); `meeting_delete` jobs for cancellations continue. I.e. the kill switch stops *new meetings and joins*, never cleanup.
- `FEATURE_ZOOM_EMBED` (client-visible) — `embedded` vs link-out join payloads; the hardware-gate dial. Off = join endpoint returns `mode:'link'` with the raw URL to authorized personas only.
- `FEATURE_ZOOM_RECORDINGS` — **permits the §12 consent-gated enablement workflow** (consent capture, the enable-recording PATCH once all expected participants accept, pipeline enqueue). It never enables cloud recording directly at provision — provisioning always sends `auto_recording:'none'` regardless of this flag; with the flag off, the enablement job simply never runs and sessions stay unrecorded. Read-back verification alerts if the effective provision-time value is anything but `'none'` (verified: create response reflects effective values on capability/settings mismatches).
- `FEATURE_AI_MINUTAS` — requires the sanitizer operational (§6 predicate enforced in code regardless of flag); also gates shadow mode.
- `ZOOM_SCHOOL_ALLOWLIST` (csv of school_ids; empty = all) — checked at provision time. **School removed after provisioning**: existing future meetings are NOT auto-deleted (sessions remain valid); provisioning of new meetings stops; a reconcile notice lists still-provisioned meetings for the removed school so an admin can bulk-cancel deliberately. Documented so removal is never a silent data-loss action.
- `ZOOM_MODE=live|mock` — DI switch for the fake adapter (CI/e2e/dev).
- Secrets (server-only, never NEXT_PUBLIC): `ZOOM_S2S_ACCOUNT_ID/CLIENT_ID/CLIENT_SECRET`, `ZOOM_SDK_CLIENT_ID/CLIENT_SECRET`, `ZOOM_WEBHOOK_SECRET_TOKEN`, `SUPABASE_S3_ACCESS_KEY/SECRET`, `CRON_SECRET`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`.
