## 1. The bug — confirmed against the LIVE production schema by the PM

`lib/services/school-hours-report.ts:149-166` queries `consultor_sessions` for two columns
that **do not exist**:

```
.select(`id, title, scheduled_date, actual_duration_minutes,
         planned_duration_minutes, status, hour_type_key, ...`)
.order('scheduled_date', { ascending: false })
```

**PM verification, three independent layers:**

1. **Live production** (read-only query via the Supabase management API, which is what
   plan §0.1(d) requires of the PM anyway): of
   `scheduled_date, planned_duration_minutes, session_date, scheduled_duration_minutes,
   actual_duration_minutes`, production returns **only** `session_date`,
   `scheduled_duration_minutes`, `actual_duration_minutes`. The two named in the query are
   **not there**.
2. **Schema history**: the baseline dump's `consultor_sessions` block carries `session_date`
   and `scheduled_duration_minutes`, never `scheduled_date` or `planned_duration_minutes`,
   and no migration adds either.
3. **PostgREST rejects an unknown column** — and this project has *observed* that, not just
   read it: the Z1b regression probe recorded in `LEDGER.md` used exactly this behaviour,
   noting that "a deliberately fake column returns `42703 column does not exist`."

**The consequence.** `:149` destructures only `data`, discarding `error`. So the request
fails, `sessionRows` is `null`, `typedRows` is `[]` (`:168`), and **every hour bucket's
session drill-down in the school hours report has always been empty in production.** The
`if (sessionIds.length > 0)` guard at `:177` never holds, so the ledger sub-query beneath it
has never run either.

**Why it survived:** `fetchSchoolReportData` has **no direct test coverage at all**. Both
suites that name it — `__tests__/api/hour-tracking/school-report.test.ts:53` and
`school-report-pdf.test.ts:52` — `vi.mock` the entire module out and assert on the handler
around it. The function has never been executed by a test.
