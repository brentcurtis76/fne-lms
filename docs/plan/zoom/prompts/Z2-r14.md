`lib/types/consultor-sessions.types.ts:26,32,33` declares `session_created`,
`session_rescheduled` and `session_cancelled` as session notification types. **None of the

## 2. PM RULINGS — settled, do not re-derive

Four rounds of this phase ended in `STATUS: FINDINGS` because a PM ruling was vague or
self-contradictory, and **every time the fault was the PM's**. These are stated precisely
so you do not have to guess. If any two of them conflict with each other or with something
you find in the code, **that is a fifth PM error — stop and report `FINDINGS`.**

**Ruling 1 — `session_created` fires at APPROVAL, not at creation.**
`pages/api/sessions/index.ts:225` sets `status: 'borrador' as const` unconditionally on
every create — PM-verified, there is no branch that creates a session in any other status.
A `borrador` session is not participant-visible and must notify nobody. Approval is also
where Z2-1 enqueues Zoom provisioning, so it is the moment the session becomes real in both
senses. **Emit from `[id]/approve.ts` and `bulk-approve.ts`. `pages/api/sessions/index.ts`
gains no emitter.**

**Ruling 2 — recipients are the session's own people, and the set does not widen.**
The deduplicated union of `session_facilitators.user_id` and `session_attendees.user_id`,
derived exactly as `pages/api/cron/session-reminders.ts:82-95` derives it (a `Set`, both
arrays, skip falsy `user_id`). No admins, no consultants-by-school, no growth-community
members. These are people already on the session, so no disclosure boundary moves. If the
resulting set is empty, emit nothing and do not error.

**Ruling 3 — the payload carries the platform URL and never the raw link.**
`buildAbsoluteUrl(buildSessionJoinPath(id), req)` — `buildAbsoluteUrl` is
`lib/utils/app-url.ts:120`, `buildSessionJoinPath` is exported from
`lib/utils/session-disclosure.ts`; the pattern is `pages/api/cron/session-reminders.ts:108-111`.
**`consultor_sessions.meeting_link` must never appear in a notification payload.** Zoom's
`join_url` is passcode-embedded and secret-equivalent; notification payloads are persisted
in the event log and rendered into e-mail. This is the invariant Z1a's entire disclosure
remediation exists to protect. Where there is no meeting, pass `null` — same as the
reminder does.

**Ruling 4 — emit after the write commits, and never fail the request.**
The notification is emitted only once the session row is actually changed, never
optimistically before. Wrap the emission in `try/catch`, log the error, continue — the
pattern is `pages/api/sessions/edit-requests/[eid].ts:314-328`, which does exactly this
around `session_edit_request_approved`. A failing notification must never turn a successful
approval, reschedule or cancellation into an error response.

**Ruling 5 — one helper, not six copies.**
This workstream's standing pattern is a single canonical derivation consumed everywhere
(`lib/utils/session-scope.ts`, `lib/utils/session-disclosure.ts`,
`lib/services/billable-hours.ts`). Six inline emitters would drift. Write **one** helper —
name and exact signature are yours — that takes the session (or its id), the event kind,
the request, and whatever a reschedule needs, and does the recipient derivation, the URL
build, the trigger call and the swallow-and-log. The six routes call it.
