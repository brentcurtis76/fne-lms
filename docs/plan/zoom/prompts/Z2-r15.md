## 3. FINDING 3 (SHOULD-FIX, fix it here) — the recipient query swallows its errors

`collectParticipantIds` (`lib/services/session-lifecycle-notifications.ts:126-155`)
destructures only `data` from both Supabase reads. A failed `session_facilitators` query
yields `data: null`, the loop adds nobody, and `notifySessionLifecycle` then treats the
empty union as *"a session with nobody on it is a normal state"* and returns **silently**.

A read error and an empty session are not the same event, and this module cannot currently
tell them apart. **This is the same defect class round r11 was dispatched to repair one
chunk ago** — a failed query masquerading as "there is nothing here" — so it does not get to
ship in new code written after that ruling.

**The remedy, within invariant 3 (a notification failure is never the caller's failure):**
capture both errors, log them distinctly enough that a silent under-notification is
diagnosable from the logs, and make "query failed" visibly different from "nobody is on this
session". You choose whether a partial read still notifies whoever was found or notifies
nobody — **state which and why**; both are defensible and the PM will not overrule a reasoned
choice, only an unstated one.
