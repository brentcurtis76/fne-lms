## 1. THE MECHANISM YOU ARE IMPLEMENTING

RFC 5545 §3.8.7.4: a calendar client decides whether an incoming event **replaces** one it
already holds by matching `UID` and comparing `SEQUENCE`. A higher `SEQUENCE` for the same
`UID` is a revision; an equal or absent one is not, and most clients simply ignore it.

The builder already gets the `UID` right — `id: \`${session.id}@genera.fne.cl\``
(`lib/utils/session-ical.ts:202`), stable across re-exports of the same session, which is
exactly what makes `SEQUENCE` work. The event data goes through `ICalEventData` at `:201`
and `cal.createEvent(eventData)` at `:234`; `ical-generator` accepts a `sequence` field on
that object.

## 2. PM RULINGS — settled, do not re-derive

**Ruling 1 — `SEQUENCE` = whole seconds between the session row's `created_at` and its
`updated_at`.**

Verified by the PM before writing this: `consultor_sessions` carries both columns, and
`updated_at` is maintained by a **database trigger** on every update —
`trg_consultor_sessions_updated_at BEFORE UPDATE … EXECUTE FUNCTION set_updated_at()`
(`supabase/migrations/00000000000000_baseline.sql:15376`). So the value rises on every
change to the row without any code remembering to bump it, which is the property that
matters.

Why this and not the alternatives: a dedicated `revision` column would be cleaner and is a
**migration**, which this chunk must not carry; raw epoch seconds would be monotonic but
enormous and would collide with the int32 ceiling some clients enforce. Seconds-since-
creation is monotonic per session, starts at 0 for a never-updated row, and stays small for
any realistic session lifetime. Clamp at 0 — never emit a negative `SEQUENCE`.

**If either column turns out to be absent, nullable in practice, or not actually maintained
on the update paths, STOP and report `FINDINGS`.** Do not invent a fallback that silently
emits a constant, which would reproduce today's defect while looking fixed.

**Ruling 2 — every .ics surface gets it, or the fix is worthless.** A participant may hold
an event that arrived from any of the three endpoints; a revision that bumps on one surface
and not another is worse than none, because the client keeps whichever it saw last with the
highest sequence. All three must carry it:
`pages/api/sessions/ical.ts`, `pages/api/sessions/[id]/ical.ts`,
`pages/api/sessions/series/[groupId]/ical.ts`.

**Ruling 3 — extend `ICalSessionInput`, do not widen what the module reads.** The interface
at `lib/utils/session-ical.ts:22-40` is the module's contract and the reason it never sees
`meeting_link` (see its own doc at `:16-20`). Add the two timestamp fields to it and have
each endpoint pass them. **Check what each endpoint actually selects** rather than assuming
`select('*')` — if one projects columns explicitly, it needs the two fields added.

**Ruling 4 — a cancellation is a revision too.** `mapStatusToICalStatus`
(`lib/utils/session-ical.ts:47-54`) already emits `STATUS:CANCELLED`, and cancelling writes
the row, so the trigger raises `updated_at` and the sequence rises on its own. Assert that
rather than assuming it: an .ics whose STATUS flipped to CANCELLED but whose SEQUENCE did
not move is a tombstone the client will ignore.
