## 2. PM RULINGS — settled

**Ruling 1 — the preview needs the date, so it renders only when there is one.**
`formatSessionTimeForConsultant` takes `(sessionDate, timeString)` because the offset is not
constant: Chile and Spain observe DST in opposite hemispheres, so the same 09:00 is 14:00 in
some months and 15:00 in others. With no date chosen, **render no preview** — do not guess,
do not use today's date, and do not show a fixed offset.

**Ruling 2 — preview, never a second input.** The Spain time is read-only, derived on every
render from the Chile values. There is no Spain input and nothing about Spain is stored or
submitted. Any design where a user can type a Spain time is wrong.

**Ruling 3 — use the existing helper. Do not write a second conversion.** If you need a
range (`"15:00 a 16:00 (hora España)"`) rather than a single time, build it *from*
`formatSessionTimeForConsultant`, or add one small exported helper **in
`lib/utils/session-timezone.ts` beside it**. One module owns this conversion. A second
implementation in a component is the drift this workstream keeps eliminating.

**Ruling 4 — both scheduling surfaces, not just the pretty one.** A time is set in two
places and both get the treatment:
- `pages/admin/sessions/create.tsx` — the two inputs at `:1105-1131`, state at `:88-89`
- `components/sessions/EditRequestModal.tsx` — `startTime`/`endTime` state at `:27-42`

The edit-request modal is arguably the more important of the two: it is where a consultant
proposes a move, and it is the path that now emits `session_rescheduled` (chunk Z2-4a).
