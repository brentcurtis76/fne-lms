## 1. THE TRUST BOUNDARY — read this before designing anything

The Zoom integration has exactly two schemas and the split is a **frozen §6/§7 decision**:

- **`zoom_internal.zoom_meetings`** — `supabase/migrations/20260729120100_zoom_internal_tables.sql:98`.
  Its own `COMMENT ON TABLE` says: *"Secret-bearing (mn, plaintext passcode, join_url) —
  never leaves this schema."*
- **`public.session_meetings_public`** — `supabase/migrations/20260729120300_session_meetings_public.sql:20`.
  Its `COMMENT ON TABLE` says: *"status/join-window/has_recording only — **zero secret
  fields by construction**."*

**PM RULING 1 — dial-in data goes in `zoom_internal.zoom_meetings` and NOWHERE ELSE. The
public projection gains no column in this round or any later one.**

The reasoning, so you can defend it rather than just obey it: the phone numbers themselves
are not secret — Zoom publishes them. But **a dial-in that a human can actually use needs
the meeting number and the participant passcode too**, and those are exactly the two values
the internal schema exists to contain. Splitting the set across two trust levels — numbers
in `public`, credentials in `zoom_internal` — creates a half-useful public row whose obvious
next "fix" is to add the rest. Keep the whole set on the secret-bearing side, and let it
reach a participant later through the authorized join endpoint, which already mints
per-click credentials behind the join policy. **That is chunk Z2-4e. Do not build it here.**

If you conclude the public projection must change, **stop and report `FINDINGS`** — that is
a plan-level decision, not a chunk-level one.

## 2. PM RULINGS — settled

**Ruling 2 — dial-in must NEVER block provisioning.** Zoom returns dial-in numbers only for
accounts with the relevant audio plan; a tenant without one returns none, and the meeting is
still perfectly good. `assertCreateResponse` (`lib/zoom/api.ts`, the validator documented as
checking *"the fields `meeting_provision` PERSISTS or JOINS WITH, and no others"*) exists
because a `{}` body once mapped cleanly to a provisioned row with nothing to join. **Dial-in
is the one persisted field that must be OPTIONAL there.** Absent ⇒ store null/empty and
carry on. If you make it required, you turn a missing audio plan into a failed provision.

**Ruling 3 — store what Zoom reports, do not normalise it into a new vocabulary.** Zoom
returns the numbers under the meeting's `settings` (`global_dial_in_numbers`), each entry
carrying country, country name, city, number and type. Persist the reported shape as `jsonb`.
A future country filter or "show the Chilean number first" belongs to the UI chunk, working
off the stored data — not to a lossy transform applied on the way in. **Do not invent a
relational table for this**; it is per-meeting reference data, read as a unit.

**Ruling 4 — the fake adapter must produce it, or CI proves nothing.** `ZOOM_MODE=mock`
(`lib/zoom/fake.ts`) is what every blocking CI run exercises — no CI job holds Zoom
credentials. A capture path the fake never produces is a path no gate ever executes. The
fake must return a synthetic dial-in set, **and at least one test must drive the
tenant-without-dial-in case too**, since ruling 2 makes that a supported outcome rather than
an error.

**Ruling 5 — the new column is inside the isolation boundary and must be proven so.**
`supabase/tests/002-zoom-internal-isolation.sql` is the pgTAP suite that holds the §6/§7
line. Extend it so the new column is covered by the same proof as the rest of the table —
an anon/authenticated role must not be able to read it.
