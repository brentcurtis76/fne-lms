## 2. THE RULING — Option A, and why

**Adopt r18's Option A.** Add the column, and derive it **inside the two existing RPCs at
their unchanged 6-argument signature** via `CREATE OR REPLACE FUNCTION`.

**The check that decided it, which the PM ran rather than assumed:** `effective_settings`
has **exactly two writers in the entire codebase**, and both are the `UPDATE … SET` inside
those two RPCs (`20260731120000_zoom_provision_rpcs.sql:46` and `:104`). Nothing else ever
updates it — `meeting-provision.ts:2059` only *reads* it. **Therefore a column set in the
same `UPDATE` statement cannot drift from its source**, which was the one serious objection
to a derived column. Add a writer of `effective_settings` in future and you must add the
column there too; the column `COMMENT` must say so.

Option A is additive (no `DROP`, no overload), leaves every pgTAP signature assertion valid,
and matches the established idiom for this file — its own header says **"AMENDED IN PLACE"**
(`:3`), which is precisely `CREATE OR REPLACE` at an identical signature.

**Option B (generated column) is REJECTED** — r18's reason stands (there is no persistence
step left to mutate, so [F7] could not be honest), plus a generated column could never hold
a backfilled value from any other source.

**Option C (DROP + recreate with 7 params) is REJECTED.** It is what the r18 prompt
literally asked for, and asking for it was the PM's error. It breaks a RED-tier repo rule
for a marginal gain in explicitness, and it carries a production-ordering hazard the local
gate cannot see: between `DROP` and `CREATE` the function does not exist, and this project
has already shipped unapplied migrations once (Z1b, session approval broken in production
after ten green review rounds).

**Consequences you should not have to infer:**
