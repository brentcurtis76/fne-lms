## 1. THE FINDING — [B1] a session toggled to managed keeps its manual meeting_link

**Verified by the PM against the code, not inferred.** Three facts compose into the
defect:

1. `pages/api/sessions/index.ts:129-130` — an **unmanaged** `online`/`hibrida` session
   **cannot be created without a `meeting_link`** (400). So every unmanaged online
   session in the database has one.
2. `pages/api/sessions/[id]/index.ts:305-315` — an admin **may** set
   `is_zoom_managed: true` while the session is `borrador` / `pendiente_aprobacion`.
   This is the path r1 was explicitly told to allow, and it is correct that it exists.
3. The update that follows copies only the allow-listed fields
   (`pages/api/sessions/[id]/index.ts:333-345`); **`meeting_link` is never touched.**
   Your own test proves it: `__tests__/api/sessions/session-managed-link-guard.test.ts:204-212`
   asserts `expect(state.updates[0]).toEqual({ is_zoom_managed: true })`. The gap is
   invisible only because that fixture carries `meeting_link: null`
   (`:95`) — the one shape the real world cannot produce for an online session.

**Result:** the ordinary, blessed path leaves a **managed session carrying a stale
manual link**. At approve time the provisioner mints a real Zoom meeting while the
source row still advertises a different link to every consumer that reads
`meeting_link`. That is exactly the two-rival-links confusion plan §8's durable-intent
design exists to prevent — §8 is explicit: *"`consultor_sessions.meeting_link` stays
NULL for managed sessions — no raw-link write-back anywhere."*

It is also self-trapping: once the row is managed, `:279-288` refuses every non-null
`meeting_link` write, so the stale link cannot be corrected by the obvious edit.

This is blocking rather than backlogged under this workstream's standing rule (recorded
2026-07-29): **known defects in reviewed code are never filed as open items.**

## 2. PM RULING — how to fix B1 (do not choose for yourself)

Two designs were considered. **Adopt option B.**

- ~~Option A: reject the toggle-on when a `meeting_link` is stored (409, "clear the
  link first").~~ Rejected: it dead-ends the admin on a field that was *mandatory* at
  creation, and it makes the blessed path fail for the majority shape.
- **Option B (ADOPTED): turning managed ON forces the managed shape in the same
  update** — `meeting_link` → `null` and `meeting_provider` → `'zoom'`, written
  atomically with the flag. This makes PUT behave exactly like POST already does
  (`pages/api/sessions/index.ts:141-145` forces the provider; `:219-221` forces the
  null link), so one rule governs both entry points instead of two that disagree.

Discarding the manual link **is** the intended semantic of "the platform now owns this
meeting". Say so in a comment at the site so the next reader does not mistake it for
data loss.

Scope of the ruling, precisely:

- It applies only on the **transition** — stored `is_zoom_managed !== true` and the
  request sets it to `true`. A PUT that merely re-sends `is_zoom_managed: true` on an
  already-managed session changes nothing extra (the r1 guards at `:279-288` already
  cover that row).
- Turning managed **OFF** is out of scope and must not grow new behaviour: leave the
  link null. (An online session with a null link is already reachable today — PUT has
  never required a link — so this introduces nothing new. Note it under NOT DONE.)

For **B2**: mirror the POST rule — refuse the toggle-on when `modality` is neither
`online` nor `hibrida`, **400**, es-CL, wording consistent with
`pages/api/sessions/index.ts:121-125`. Order it before the option-B forcing so a
refused request writes nothing.
