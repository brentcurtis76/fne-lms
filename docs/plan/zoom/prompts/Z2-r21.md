## 1. ITEM 1 — remove the `DROP` from `20260805120000_reschedule_hours_rpc.sql`

**The finding, PM-verified.** That migration contains
`ALTER TABLE public.session_activity_log DROP CONSTRAINT IF EXISTS
session_activity_log_action_check;` at **`:50`**, then re-adds a widened allowlist at
`:53-66` and validates at `:68-69`. Its own header at `:25` declares "ADDITIVE ONLY: no DROP
TABLE, no TRUNCATE, no destructive ALTER", and `:41-44` argues that a CHECK widening is
"mechanically DROP + ADD — that mechanism is not a destructive ALTER".

**That argument loses.** `CLAUDE.md` states the rule without a mechanism exemption: *"NEVER
`DROP`, `TRUNCATE`, or destructive `ALTER`; schema changes are additive only."* The
reasoning is also sound on its own terms — the widened list is a strict superset and the
ordering is production-safe — but **a hard rule that yields to a good argument is not a hard
rule**, and this project's rules exist because it has already broken production once.

**This is the PM's error, not yours or the previous executor's.** The PM approved this
migration in an earlier round without checking it for `DROP`, and then two rounds later told
a different executor that a `DROP FUNCTION` was RED-tier forbidden. The inconsistency is the
PM's and Sol caught it.

**THE RULING — Sol's primary remedy, and it needs no schema change at all.**

Record the revision using an **already-allowed `action`** plus a **typed
`details.event_type`**. The allowlist's pre-existing 16 values are listed verbatim at
`:56-64`; `'edited'` is the natural carrier. Put the discriminator in the `details` jsonb —
e.g. `details->>'event_type' = 'hours_revised'` — so the revision history stays queryable on
its own, which was the original rationale for a distinct action.

**Then delete the entire constraint block (`:47-72`, DROP + ADD + VALIDATE + the
`COMMENT ON CONSTRAINT`) from the migration.** The migration keeps its RPC and loses its
schema change.

**Two things to handle, not to discover the hard way:**
- **Local databases already carry the widened constraint.** Removing the block means a fresh
  replay produces the original 16-value allowlist while an existing local DB keeps 17. Both
  accept everything this round writes, so it is safe — but **prove it by resetting and
  replaying**, not by reasoning. Production has never had either version.
- Anything already writing `action = 'hours_revised'` must move to the new shape, including
  tests and any pgTAP that asserts on it.

**If you conclude an already-allowed action genuinely cannot carry this** — for example
because an existing consumer would misread `'edited'` — **stop and report `FINDINGS`**. Sol's
finding names an additive schema alternative as the fallback, but it needs Brent's explicit
approval and is therefore not yours to choose.

## 2. ITEM 2 — one transactional RPC for both reschedule flows

**The finding, PM-verified.** `public.reschedule_session_hours(p_session_id, p_actor_id)`
(`20260805120000:82`) reads a session that **has already been updated** and reconciles the
ledger afterwards. Both routes therefore do the schedule write and the ledger write as **two
separate PostgREST calls**:

- `pages/api/sessions/[id]/index.ts` — the admin PUT: updates `consultor_sessions`, then
  calls the RPC through `lib/services/hour-tracking.ts:578`.
- `pages/api/sessions/edit-requests/[eid].ts` — the edit-request approval: same pattern.

A failure between the two leaves **the session moved and the ledger stale** — the school is
billed for the old duration on a session that now has a new one. Nothing rolls back.

**THE RULING.** Replace both with **one service-role-only RPC that performs, in a single
transaction:** the source-schedule update on `consultor_sessions`; the ledger `hours` update;
the planned snapshot; the ledger's date and over-budget state; and the **append-only revision
row** (per item 1's shape). **Either all of it commits or none of it does.**

Requirements that are not negotiable:

- **Atomicity is the deliverable.** A failure at any step must leave **both** the source
  session and the ledger byte-identical to their pre-call state. `[H4]` makes you prove it
  by injecting a failure, not by asserting the happy path.
- **Optimistic concurrency is preserved.** The admin PUT accepts `if_updated_at` and guards
  the update with it (`pages/api/sessions/[id]/index.ts`, the `ifUpdatedAt` branch). That
  guard must survive **inside** the new RPC — a caller passing a stale timestamp must be
  rejected, and rejected without having written anything.
- **Service-role only**, `SECURITY DEFINER`, `SET search_path = ''`, signature-specific
  grants, matching the discipline in `supabase/migrations/20260731120000_zoom_provision_rpcs.sql`
  (its header documents the pattern) and asserted in pgTAP the way that file's functions are.
- **No `DROP`, no overload, no signature change to any existing function.** If you need a
  different signature, write a **new** function with a new name and leave the old one in
  place; report what you left behind. `CREATE OR REPLACE` at an identical signature is the
  established idiom for amending in place.
- **Both routes must end up calling the same RPC.** One implementation, no drift — the rule
  that produced `lib/utils/session-scope.ts`, `lib/services/billable-hours.ts` and
  `lib/services/session-lifecycle-notifications.ts`.

**Preserve every behaviour the routes have today** that is not the atomicity defect: the Zoom
`meeting_sync` enqueue, the `session_rescheduled` notification and its value-based
`hasScheduleChanged` gate, the disclosure rules, the response bodies. **If moving the write
into the RPC changes when the notification or the enqueue fires, say so explicitly in the
report** — that ordering was ruled on in earlier rounds and the PM needs to re-rule it, not
discover it.
