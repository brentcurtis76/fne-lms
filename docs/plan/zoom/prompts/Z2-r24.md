## 1. THE RACE

`claim_zoom_jobs` (`supabase/migrations/20260729120200_zoom_jobs_rpcs.sql`) leases jobs with
`FOR UPDATE SKIP LOCKED`, which guarantees **two tickers never lease the same job row**. It
guarantees **nothing about two different jobs for the same surface**. Vercel crons overlap by
design — the file's own header says so — so a `meeting_provision` and a `meeting_delete` for
one session can be in flight at the same time.

**The interleaving Sol named:**

1. `meeting_provision` checks eligibility — the session is `programada`, so it proceeds.
2. The session is **cancelled**. `consultor_sessions` flips to `cancelada`, the hours
   reservation is released, and `meeting_delete` is enqueued.
3. `meeting_delete` runs. The row still has no `zoom_meeting_number` — nothing has been
   created yet — so it finds nothing to delete and completes.
4. `meeting_provision` resumes, creates the meeting at Zoom and persists it.

**Final state: a live Zoom meeting nobody will ever attend, attached to a cancelled
session.** The delete already ran and will not run again.
