## 1. ITEM 8 — a failed ledger query reads as "no hours"

**PM-verified.** `lib/services/school-hours-report.ts:143` fetches the bucket summary:

```ts
const { data: bucketRows, error: bucketError } = await serviceClient.rpc('get_bucket_summary', {
  p_contrato_id: contrato.id,
});
```

and the surrounding loop **continues** on error. A failed query is therefore indistinguishable
from a contract with no hours, and the report renders as though the school has none.

This is the **same defect class round r11 was dispatched to repair one chunk earlier**, and
the PM logged it as "unruled" across three later rounds without ruling it. Sol found it.
**That is the PM's failure, not yours.**

**THE RULING — fail, do not degrade.** When the ledger query **fails**, the report fails. The
scheduled fallback is used **only after a successful query proves a session genuinely has no
row**. A number a school might be invoiced against must never be quietly synthesised from a
failed read.

You choose how the failure surfaces to the caller — an error result, a thrown error, a 500 —
**state which and why**, consistent with how this service already reports failure.
