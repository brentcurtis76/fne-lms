## 1. MINOR 1 — the failed-compensation message can claim a host slot that is already free

`lib/zoom/jobs/meeting-provision.ts:2050-2055, 2065-2104, 2707-2709`

`holdsReservation` records **what the caller knew before awaiting the Zoom DELETE**. A
concurrent `meeting_delete` can retire the numberless row while that request is in flight. If
the DELETE then fails, the operator message says the reservation *"keeps blocking its host"* —
**and the row is already retired, so it does not.**

The durable marker, the Zoom meeting number and the required manual action are all still
correct, so this is triage accuracy, not a compensation failure. But it sends an operator
looking for a block that is not there, and this project has already ruled once (r27, the
`no_meeting_row` dead-letter) that **a signal a human must act on has to be true, or it trains
people to distrust the channel.** Same principle.

**THE RULING — Sol's option B, the state-neutral one.** Do **not** re-read the row after a
failed DELETE to re-classify it: that is another round trip on an error path, and the answer
could be stale again by the time it is read. Instead make the operator copy **state-neutral**:
always name the Zoom meeting number and the required cancellation action, and **stop asserting
anything about the host slot** in the failure message.

The `holdsReservation` argument may stay if it still earns its place elsewhere; if the copy no
longer needs it, remove it rather than leaving a parameter nothing reads. **State which you
did and why.**

**Behaviour must not change**: the park, the status preservation, the durable marker, the
`meeting_delete` refusal and the ambiguous-park precedence all stay exactly as they are. Only
the sentence changes.

## 2. MINOR 2 — the numberless precondition has no negative control

`lib/zoom/jobs/meeting-provision.ts:2195-2204` ·
`__tests__/lib/zoom/jobs/meeting-provision.test.ts:4058-4149`

The r29 regression test proves the **positive** case: a retired **numberless** row with a
matching checkpoint is compensated. **Nothing proves the negative** — that a retired row
**already carrying a `zoom_meeting_number`** must *not* enter that branch.

**The PM found this by mutation and Sol confirmed it independently:** deleting
`held.zoom_meeting_number === null` from the predicate passes **all 116** tests in that suite.

The predicate is correct. What it guards is an **ownership boundary**: a numberless retired row
is the one whose retirement *proves* `meeting_delete` never called Zoom, so this process still
owns the meeting. A retired row **with** a number was deleted by a writer that **did** call
Zoom — that meeting is not ours to remove, and compensating it would have this process issue a
DELETE against a meeting another writer already owns.

**THE RULING — add the negative control**, per Sol's fix block: an ineligible session, a
retired row **carrying** `zoom_meeting_number`, and a matching created checkpoint. Assert the
Zoom DELETE is **not** called and that the row and projection are **unchanged**.
