## 2. SCOPE — chunk Z2-3a: the atomic pre-execution reschedule

**Hours only. No Zoom in this chunk at all** — `meeting_sync` and `meeting_delete` are
Z2-3b. That separation is deliberate: this half is pure ledger integrity and must be
reviewable on its own terms.

**S1 — one transactional RPC**, in a new migration (`supabase/migrations/<ts>_reschedule_hours_rpc.sql`,
timestamp strictly greater than `20260804120000`). It performs, atomically:

1. recompute the ledger `hours` from the session's new planned duration;
2. update `contract_hours_ledger.planned_minutes_snapshot` to the new minutes;
3. insert a `session_activity_log` revision row recording **old minutes, new minutes,
   actor, timestamp**.

All three commit or roll back together. §11 is explicit about *why* this must be an RPC
rather than three statements from the route: the existing activity-logging path is
best-effort and will not fail an update on its own, so a route-level sequence can leave
the ledger updated with no revision trail.

**S2 — the pre-execution guard, inside the transaction.** The recomputation applies
**only** while the session is pre-execution (`programada`). At `en_progreso` or beyond,
and for a finalized ledger row, planned values are **frozen** — the only path that may
change them is the Z7 admin override, which does not exist yet. The guard lives in the
RPC, not only in the caller, because the caller is not the security boundary.

**S3 — wire both reschedule paths.** Call the RPC from `handlePut` in
`pages/api/sessions/[id]/index.ts` and from the approve branch of
`pages/api/sessions/edit-requests/[eid].ts`, **only when the applied change actually
alters the planned duration** (`start_time`/`end_time`; a pure `session_date` move
changes the date but not the duration — it must still update `session_date` on the
ledger row, which is a column that exists and is currently never maintained).

## 3. PM RULINGS — do not choose differently

1. **`hours > 0` is never violated and the CHECK is never dropped or altered.** If a
   recomputation would produce `0`, the RPC **raises** and the whole reschedule fails.
   The zero-waiver case is Z7's `effective_minutes` column, deliberately additive
   precisely so this constraint stays untouched (§11, v2.1.1). Dropping or relaxing that
   CHECK is a stop-and-report condition.
2. **Additive migration only.** No `DROP`, no `TRUNCATE`, no destructive `ALTER`, no RLS
   change, no new grant beyond the RPC's own narrow `GRANT EXECUTE`. Follow the
   `REVOKE` → `GRANT` pattern at `20260731120000_zoom_provision_rpcs.sql:250-268`.
3. **The revision row is append-only in spirit: never update or delete a prior
   `session_activity_log` entry.** Its `action` value is yours to choose but must be new
   and specific (not a reused `'edited'`), so the revision history is queryable.
4. **Budget behaviour on a lengthening reschedule.** If the new duration exceeds the
   contract's available hours, **do not block the reschedule** — set `is_over_budget`
   on the ledger row, exactly as `createReservation` already does at approve
   (`hour-tracking.ts:245-330` — read it and match its semantics rather than inventing
   parallel ones). Rescheduling is an operational act; the over-budget flag is the
   existing signal.
5. **Do not refactor `createReservation`, `completeReservation` or
   `executeCancellation`.** Cancellation clauses (`devuelta`/`penalizada`) are a fully
   separate flow (§11) and must not be touched.
6. **No Zoom.** No `meeting_sync`, no `meeting_delete`, no enqueue, no import from
   `lib/zoom/**`. If a §11 rule seems to require one, stop and report.
