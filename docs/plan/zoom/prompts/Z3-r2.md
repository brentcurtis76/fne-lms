## SCOPE

### 1. ZAK retrieval in the integration layer

There is **no ZAK support anywhere** — `grep -n "zak\|ZAK\|token:admin" lib/zoom/client.ts
lib/zoom/api.ts lib/zoom/fake.ts` returns nothing. Add it in all three, following the exact
patterns those modules already use for other calls (typed errors, 429 `Retry-After`
handling, the `ZoomApi` interface + in-memory fake seam):

- **REST**: `GET /users/{userId}/token?type=zak`, requiring the `user:read:token:admin`
  scope. `{userId}` is `zoom_hosts.zoom_user_id`.
- **`ZoomApi` interface method** so `ZOOM_MODE=mock` works with no Zoom secrets — every
  blocking CI gate runs in mock mode, so a real-only implementation fails CI by construction.
- **The fake must be faithful to the traps**, as the existing fake is: a ZAK is a bearer
  credential with a ~2 h life, and the fake should make an expired or missing one an
  expressible state, not just return a happy string.

**§5, verbatim, on how ZAK is handled:** *"ZAK (host credential, 2h) — fetched at
start-click (`user:read:token:admin` scope), **never persisted**; `start_url` — never used
or stored."* Do not write a ZAK to any table, any log, any cache, or any job row.

### 2. The §9 issuance rule — this is the security core of the chunk

**§9's rule, verbatim, and it is precise on purpose:**

> `role:1` + ZAK issued only to (a) the **assigned facilitator**, and only for **their own**
> mapped host identity (`profile_id = facilitator` AND that host is the meeting's
> `host_zoom_user_id`); (b) **admins**, but only for **organization-controlled pool
> identities** (`profile_id IS NULL`) or explicitly FNE-owned accounts flagged
> `org_owned=true` — an admin never receives a consultant's personal ZAK. Every issuance
> writes a `zak_issued` audit event. Other consultants — even same-school — never receive
> host credentials. If a meeting is hosted on a consultant's personal identity and that
> consultant is absent, an admin's path is host-reassignment to a pool identity
> (re-provision job), not impersonation.

The table you need **already exists** — Z1b built it for this:
`zoom_internal.zoom_hosts` (`supabase/migrations/20260729120100_zoom_internal_tables.sql:35-45`)
carries `zoom_user_id` (unique), `email`, `profile_id uuid REFERENCES public.profiles(id)`
(**NULL ⇒ pool host**), `is_active`, `max_concurrent`, and `org_owned boolean NOT NULL
DEFAULT false`. Its comment states the contract: *"profile_id NULL = pool host; org_owned
gates admin ZAK issuance."* `zoom_meetings.host_zoom_user_id` (`:105`) references it.

**Note what the rule does NOT say.** `decision.role === 'host'` covers both admins and
assigned facilitators, and the two get *different* treatment. Resolve the persona properly;
do not collapse them. A facilitator whose meeting is hosted on someone else's identity gets
**no ZAK** — and per §9 the answer is not impersonation, so they fall back to link mode
exactly as ruling ③ falls back.

### 5. SHOULD-FIX carried from r1 — fix it here

`buildSdkJoinPayload` currently receives `passcode: typeof meeting.passcode === 'string' ?
meeting.passcode : ''`. **Make a missing or blank passcode return `null`** (⇒ link mode)
instead of shipping `passcode: ''`.

Why, so you can judge the change rather than apply it blindly: an empty passcode makes the
browser join fail at Zoom with an opaque error **and no fallback**, where link mode would
have worked — the opposite of ruling ③'s direction. The PM verified the state is

bar stays `pending` with NULL `join_url`, which outcome 8 gates on at `join.ts:349` on this branch), so this
is a defensive default aimed the wrong way, not a live bug. Fix it because you are already
inside the function.
