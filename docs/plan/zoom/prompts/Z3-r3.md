## PM RULINGS — decided. Implement them; do not re-litigate.

**① The client NEVER reads the embed feature flag. `mode` in the response is the only
signal.**

This is the most important ruling in the chunk. `isFeatureEnabled` needs `FEATURE_ZOOM_EMBED`
server-side and `NEXT_PUBLIC_FEATURE_ZOOM_EMBED` in the browser — two env vars for one flag,
the repo's pre-existing convention. If the client branched on its own copy, a deployment that
set one and not the other would produce a **split brain**: a route minting SDK payloads for a
UI that will not render them, or a UI reaching for an embed the route will not serve. Since
the server already tells the client which mode it is in, the client has no reason to ask
twice. **Do not import `featureFlags` into any client component in this chunk.** One reader,
no drift.

**② The SDK-failure fallback is a SECOND request carrying an explicit intent, never a
`join_url` smuggled into the SDK payload.**

§5 forbids `join_url` in an SDK payload, so the fallback cannot be pre-loaded. When the embed
fails — CDN unreachable, `ZoomMtgEmbedded` absent, `init`/`join` rejecting — the client
re-POSTs the same endpoint with an explicit body intent (e.g. `{ fallback: 'link' }`) and the
server honours it **by skipping the SDK branch and nothing else**.

Every gate above outcome 8 must run identically, and the response must be byte-identical to
what Z2 shipped. This cannot escalate: link mode is what the *same* persona already received
before Z3 existed, so the client is asking to be given less, not more. It is still a widening
of the wire contract, so make it narrow and explicit: an unrecognised value is ignored, not an
error, and the intent may never influence anything except whether the SDK branch is
considered.

**③ Do NOT touch `pages/meet/diag.tsx` or `pages/api/meet/diag-signature.ts`.**

`/meet/diag` is the consultores' field instrument for the hardware protocol
(`docs/planning/zoom-hw-protocol.md`), and the hardware verdict is still open — the field
gate was *waived*, not cleared (PLAN §16, amended 2026-08-08). Write `PreJoinCheck` fresh even
though diag's capability probe overlaps it. **Duplicating a probe is cheap; changing the
instrument while the protocol is live is not.** Note the duplication in your report as known
debt.

**④ Component View is DESKTOP ONLY.** Verified in the plan (§2) and in Z0B. The mobile
Client View route is **chunk Z3-4**, not this one. This chunk may render the embed on desktop
and must degrade to link mode on mobile rather than shipping a broken embed — pick a
defensible detection and state it in your report.

**⑤ The SDK loads from Zoom's CDN, not from `package.json`.** `@zoom/meetingsdk@6.2.0`
declares `peer react@"18.2.0"` exactly and this repo runs 18.3.1, so npm refuses the install
without `--legacy-peer-deps`, which would change install resolution for every CI job.

**`pages/meet/diag.tsx:43-146` is a complete, working reference — read it before writing a
line of loader code.** The two facts that are not obvious and cost real time to rediscover:

- The Component View bundle treats **React and ReactDOM as externals**. With no `window.React`
  it throws `ReferenceError: React is not defined` while evaluating and never assigns
  `window.ZoomMtgEmbedded`.
- Zoom's vendor copies (`${SDK_BASE}/lib/vendor/react.min.js`, `react-dom.min.js`) must load
  **sequentially, before** the main bundle. Parallel loading races React against the bundle
  that expects it. Those globals are inert for the rest of the page — Next.js resolves React
  through its own bundle — and this was verified empirically in Z0B (results §6).

Reuse that pattern. You may lift the loader into a shared module **as new code**; you may not
edit diag.tsx to import it (ruling ③).
