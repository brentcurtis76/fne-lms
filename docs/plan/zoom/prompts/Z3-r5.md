## M1 — the fallback reports every success as a blocked popup

**`components/sessions/JoinMeetingButton.tsx:277-285`:**

```typescript
const opened = window.open(payload.join_url, '_blank', 'noopener,noreferrer');
setOutcome(
  allowEmbed || opened
    ? { kind: 'idle' }
    : { kind: 'denied', message: POPUP_BLOCKED_MESSAGE, retry: 'fallback' }
);
```

**Per the HTML standard, `window.open()` with `noopener` returns `null` even when the tab
was created successfully.** Sol reproduced it in Chromium: popup opened, return value `null`.
So on the fallback path (`allowEmbed === false`) `opened` is *always* falsy and the user is
*always* told the popup was blocked — then offered a retry that can open a second Zoom tab.

**The test masks it.** `__tests__/components/sessions/JoinMeetingButton.sdk.test.tsx:112`
does `mockOpen.mockReturnValue({} as Window)` — a value no real browser produces under
`noopener`.

**Required:**
- Stop inferring success from `window.open`'s return value while `noopener` is in use.
- **Keep `noopener,noreferrer`.** Do not trade a security property for a detection signal.
- Sol's suggested shapes: an explicit user-facing fallback link, or synchronously open a
  safe placeholder and navigate it once the authorized response arrives. **Pick one and
  justify it** — the second keeps the click gesture, which is what popup blockers key on.
- **Fix the mock.** Any test that stubs `window.open` under `noopener` must return `null`,
  because that is what a browser returns. A test double that models an impossible value is
  worse than no test.
- The **primary** link path (`allowEmbed === true`) must stay byte-identical to Z2.

## M2 — Client View initialises before Spanish has loaded

**`JoinMeetingButton.tsx:400`** calls `sdk.i18n.load(SDK_LANGUAGE)` and does not await it,
then calls `init`. **`lib/meet/zoom-client-view-loader.ts:109`** declares
`i18n: { load(language: string): void }` — so TypeScript cannot warn you.

Zoom's Client View localization docs require language resources to load **before**
initialization. Sol tested the real 6.2.0 bundle: `load()` returns a promise, and the
language stayed `en-US` through `init`, becoming `es-ES` only after it settled.

**Required:** type `load()` with its real asynchronous return, await it before `init`, and
test that init cannot begin until localization resolves. es-ES is a settled §15 scope item —
delivering it unreliably fails it.

## M3 — a stalled load or a failed retry can hang forever

**`lib/meet/zoom-sdk-loader.ts:108-125`** — `const script = existing ?? document.createElement('script')`.
A script element that already fired `error` is reused on retry, and **it will never fire
again**, so the promise never settles. There is also no download timeout anywhere, no
deadline on Component View `init`/`join` (`JoinMeetingButton.tsx:355`), and
`awaitClientViewCall` (`zoom-client-view-loader.ts:149`) waits forever if Zoom calls neither
callback.

The link fallback only starts from the `catch` at `JoinMeetingButton.tsx:458`. **If nothing
ever throws, nothing ever falls back** — and the UI stays busy.

**This is the finding that matters most on a school network**, which is precisely the
scenario the fallback exists to cover, and precisely what the waived hardware gate would
otherwise have told us about.

**Required:** bound every transition — CDN download, `init`, `join`, and the Client View
callback wait. Remove or replace a failed script node so a retry can make progress. Add
fake-timer tests for a stalled script and for missing SDK callbacks, asserting that the
link-fallback POST happens and the busy state clears.

## M4 — Client View needs a real route, not the existing page

**This is the PM's error** (see above). `PLAN.md` §15 says **"Client View route (mobile)"**,
and Client View takes over the page: Zoom's own import guidance warns that global framework
CSS conflicts with it. `pages/meet/session/[id].tsx` inherits `_app.tsx`'s global Tailwind
(`styles/globals.css`), and `init`/`join` can **succeed** with a broken layout — so the
catch-based fallback cannot detect this failure class at all.

**Required:** give Client View a real CSS boundary — a dedicated route that does not inherit
the global stylesheet, or another vendor-supported isolation (iframe). **A new page that
still pulls in `_app.tsx`'s globals does not satisfy this**; verify the boundary rather than
assuming it. Verify the resulting layout in a real supported mobile browser or emulation.

Everything already settled stays settled: same single join opening, same credential
discipline (values in a ref, never state/props/DOM/logs), same `{fallback:'link'}` path, and
the client still never reads a feature flag (`[C11]`'s guard must cover any new module).
