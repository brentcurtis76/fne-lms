## THE THING MOST WORTH LEARNING IN THIS ROUND

r5 replaced a **known** defect (Client View inheriting global Tailwind, which breaks the
layout while `init`/`join` still *succeed* — a failure the catch-based fallback cannot
detect) with an **unverified** one: nobody knows whether Zoom's Client View runs inside an
iframe at all. The r5 executor named the unknowns themselves and was right to:

- whether the WASM media engine and its workers initialise in a framed same-origin document
- whether the iframe's `allow="camera; microphone; display-capture; autoplay; fullscreen"`
  is sufficient for `getUserMedia` there
- whether `SharedArrayBuffer`'s absence changes the path Zoom takes

**The PM accepted that trade on the argument that it moves an undetectable failure to a
detectable one** — if the SDK cannot run framed, `init`/`join` fail and the existing
fallback catches it. **That argument is only sound if the fallback actually fires.** Item 2
is where you find out.

**If Client View does not work in the iframe, that is a FINDING, not a failure of this
round.** Report it plainly with what you observed. Do not paper over it, and do not go
rebuild M4 on your own initiative — the PM and Sol need to rule on the trade with real
evidence in hand, and a third architecture invented under time pressure is how this gets
worse.
