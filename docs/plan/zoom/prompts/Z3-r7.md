## PART 2 — DEFECT B: the isolated document has no CSS, and never has

`CLIENT_VIEW_STYLE_HREFS` in `lib/meet/zoom-client-view-loader.ts:77-80` points at
`${SDK_BASE}/css/bootstrap.css` and `${SDK_BASE}/css/react-select.css`. The loader appends
them **without awaiting**, so the failure has always been silent.

**PM verified with `curl`, and located the fix:**

| URL | Result |
|---|---|
| `https://source.zoom.us/6.2.0/css/bootstrap.css` | **403** `text/plain` |
| `https://source.zoom.us/6.2.0/css/react-select.css` | **403** `text/plain` |
| `https://source.zoom.us/css/bootstrap.css` | **200** `text/css`, 119,494 b |
| `https://source.zoom.us/css/react-select.css` | **200** `text/css`, 8,941 b |

**Zoom serves these from the UNVERSIONED root.** Point at that.

**State the trade in a comment, because it is real:** the JS stays pinned at 6.2.0 while the
CSS floats. There is no versioned alternative that answers, and Zoom's own samples load it
this way — but it is a dependency that can change under us, so it belongs in the code's
comments and in your report, not discovered later by someone else.

**And close the silence.** The reason this survived r5 is that nothing checked. Make a failed
stylesheet load **observable** — at minimum logged by name; better, surfaced the way any
other degraded-embed signal is. It need not block the join (CSS is cosmetic relative to
joining), but it must not fail silently a second time.

**This also reframes something r5 proved.** r5 verified the boundary by measuring
`document.styleSheets.length` at **0** inside the frame versus 10 on `/login`, and read that
as "the app's CSS cannot reach it". It was equally evidence that **Zoom's CSS was not
arriving either**. After your fix that number should be **2**, not 0 — and a test that
asserts the app's stylesheets are absent should also assert Zoom's are **present**, or it
will keep passing for the wrong reason.
