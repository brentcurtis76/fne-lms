### B.2 PM rulings — you rule on none of these

- **[R1] Participant events get their OWN event-type set and their own apply function.** Do not
  widen `LIFECYCLE_EVENT_TYPES`: it names the two events that move a row's *status*, and a
  participant event moves none. **Both the route and `webhook-sweep` must call the new applier**,
  for the reason the lifecycle was extracted in the first place — the sweep re-applies events the
  route recorded but never applied, and two copies would drift, with the drifted copy being the
  one only the recovery path exercises.
- **[R2] Surface resolution reads `zoom_meetings`; it never writes one and never touches
  `meeting_status`.** Resolve by `zoom_meeting_uuid` first, then `zoom_meeting_number`. Unresolved
  → **ledger-only, and the caller still reports success**, exactly as the existing unknown-meeting
  path does for meetings created outside the LMS. A participant event that moved status would
  re-enter the §9 EXCLUDE active set and re-acquire a host.
- **[R3] The interval key is `participant.participant_uuid` when non-empty, falling back to the
  identity token.** Add it to the table as an additive nullable `participant_uuid text` column plus
  a **partial unique index** on `(zoom_meeting_uuid, participant_uuid) WHERE participant_uuid IS
  NOT NULL` — that is the uniqueness Codex deferred to this chunk. **Its stability across a
  joined→left pair is UNVERIFIED** (B.1: the fixtures are two different people). Build and test
  both paths, and if a fixture or Zoom's documented semantics contradict this, **return `FINDINGS`
  rather than working around it**.
- **[R4] A `participant_left` that matches no open interval writes NO row.** Ledger-only, not an
  error. `joined_at` is `NOT NULL`, so every alternative fabricates: `joined_at = leave_time`
  invents a zero-length interval that understates presence; `joined_at = actual_started_at` invents
  presence nobody observed. Z7-3's report is authoritative (§11) and supplies the truth. Same
  direction-of-failure rule Z7-1 set for the instants. (Decision Log, `PLAN.md` §15.3.7.)
- **[R5] Identity hierarchy, in this order and no other: `customer_key` → `email` → `display_name`
  → `unmatched`.** `participant.user_id` is **never** a matching key — it is per-occurrence, and
  Z0B recorded that trap explicitly. `matched_by` records the branch that answered; `user_id` stays
  NULL unless a `profiles` row was actually found.
- **[R6] Name matching is conservative or it is nothing.** Exact match after normalisation
  (trim, case-fold, collapse internal whitespace) against the **expected attendees of that
  surface**, never a repo-wide profile search, and **two candidates ⇒ `unmatched`**. No fuzzy
  matching, no partial matching, no first-name matching. A wrong match is the defect this whole
  design exists to avoid.
- **[R7] An out-of-order interval closes nothing.** If a `leave_time` precedes the matched
  interval's `joined_at`, leave the interval open and record ledger-only — **do not let a
  malformed event raise a constraint violation out of the webhook route**, or Zoom retries it
  forever against an endpoint that will never accept it. Add the
  `CHECK (left_at IS NULL OR left_at >= joined_at)` so the database still refuses the bad row, and
  make the applier the thing that never offers it one.
- **[R8] Interval matching/merging and identity matching are PURE modules** taking plain data and
  returning plain data. §11's *"reconnect intervals don't double-count"* must be a unit test over
  the pure merge, not an integration guess.
- **[R9] Everything this chunk writes carries `source = 'webhook'`.**
