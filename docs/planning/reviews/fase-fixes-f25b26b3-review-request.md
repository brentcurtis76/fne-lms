## Approved scope

The owner approved the fix plan on 13 Nov 2026 (three levels: exposed, dead ends in normal use, wrong money or data). This release holds one build of each of two phases, both with the owner's product answers:

- Espacio Colaborativo meetings (F25b, EC-R16; owner's rule of 17 Nov 2026, widened on 20 Nov 2026): a draft meeting is seen only by its creator, the people named on it (facilitator, secretary, co-editors), an active admin and an active leader of the meeting's community, until it is finalised or moved to another state.
- Espacio Colaborativo files (F26b, EC-F1, EC-F2, EC-F3; owner's answer of 20 Nov 2026, "Yes, private"): nobody lists or reads the feed's and the messages' file stores with their own sign-in; feed pictures and documents and message attachments open only through the application, for the people who may see the post or the conversation, through links that live five minutes.

The three file stores (`contracts`, `post-media`, `message-attachments`) stay public for now. Making them private needs the publisher's inventory refresh and is not part of this release; with the stores public, a file's old public address still opens it for whoever holds that address. The rest of F25 and F26 is not in this release (F26a, the signed contracts behind five-minute links, went live on 25 Nov with pull request 213).

## What changes

**Draft meetings (Espacio Colaborativo → Reuniones)**
- A meeting in the state «Borrador» is shown, with its attendee list, agreements, commitments, tasks and documents, only to its creator, its facilitator, its secretary, a person with a co-editor row on it, an active admin and an active leader of the meeting's community. Before, every member of the community saw every draft. Meetings in any other state are seen and edited exactly as before.
- «Mis borradores» in the meetings filters is not changed by this release: it lists the drafts the person may edit, and now only among the drafts the database shows them, so a person not named on a draft no longer finds it there.
- A consultor edits a draft only when named on it (creator, facilitator, secretary or verified co-editor); a consultor's general right still covers every meeting that is not a draft. Admins and the named people are unchanged.
- A person who would not see the draft cannot turn a meeting into one. «Guardar borrador» then says «Solo las personas nombradas en la reunión (quien la creó, facilitador/a, secretario/a o coeditores) pueden guardarla como borrador.» instead of showing the database's refusal, and the meeting keeps its state.
- The overdue list (`get_overdue_items`) returns the same items as before, including the assignee's own commitment or task on a draft, but a draft's title is given only to a person who sees the draft; anyone else gets «Reunión en borrador». No screen of the application calls this function today.

**Feed files and message attachments (Espacio Colaborativo → feed and Mensajes)**
- A feed post's pictures and documents open through a new route, `/api/community/post-media/<id>`: it reads the file's row with the person's own session (so the post's read rules decide) and redirects to the file signed for five minutes. With `?download=1` it answers a link that saves the file under its own name.
- A message's attachments open and download through a new route, `/api/community/message-attachments/<id>`, built the same way (the conversation's read rules decide). The message card's pictures, the preview and «Descargar» use it and never fall back to the stored address. When «Descargar» finds the session gone it says «Tu sesión expiró. Vuelve a iniciar sesión para descargar el archivo.»; any other failure says «No se pudo descargar el archivo. Inténtalo de nuevo.»
- Someone who may not see the post or the conversation, a removed attachment, another community's file and an unknown id all get the same «Archivo no encontrado» (404); a visitor who is not signed in gets «No autorizado» (401). Every answer of both routes, the redirect included, carries `Cache-Control: private, no-store`, so the next person in the same browser is asked again (send-back 1).
- In the attachment preview, a video or an audio whose five-minute link runs out while it plays asks the route again (so the permission check runs again) and continues at the same position, playing if it was playing (send-back 1). An error within 60 seconds of the previous renewal is not an expired link: the player gives up and shows the usual error, so a renewal can never repeat without end (send-back 2).
- New posts and new attachments store the file's key instead of a permanent public address. Older rows keep opening from the key inside their stored address; nothing is rewritten.
- A feed upload that fails still says which file failed and keeps the text and the chosen files in the window («No se pudo subir «<archivo>». La publicación no se guardó; inténtalo de nuevo.»). That sentence was already on main; it was checked again by sight because the store's rules changed.

## Database

Two migrations, add-only, with no statement that deletes or changes rows:
- `supabase/migrations/20261125101000_meeting_drafts_named_people.sql`: one new function `public.can_see_meeting_draft(uuid, uuid)` (STABLE, SECURITY DEFINER, executable by authenticated and service_role only); one new restrictive SELECT rule on `community_meetings`, `Drafts are seen only by the people named on them`; three functions replaced with the same signature and attributes: `public.can_read_meeting_content(uuid, uuid)` (a draft's content only for the people above), `public.can_edit_meeting_verified(uuid, uuid)` (a consultor's general right no longer covers a draft) and `public.get_overdue_items(uuid, uuid)` (its body unchanged except the title of a draft; its grants restated).
- `supabase/migrations/20261125102000_espacio_files_private.sql`: `public.file_store_allows(text, text, uuid, text, uuid)` replaced with exactly its live body plus one branch: for `post-media` and `message-attachments`, reading and listing are refused to everyone, while uploads, replacements and removals are left to the existing rules. No rule on `storage.objects` and no store is created or altered; the four `file_stores_boundary_*` rules already call this function.

No table, rule or function of earlier releases is dropped, no row is changed. None of the five functions created or replaced holds a DELETE or TRUNCATE statement (the word "delete" appears only as a storage action name in `file_store_allows`), so no function of this release deletes rows and `.pm-publish/solo-preflight.json` declares none (it is unchanged: no checks, no declarations). The publisher's own reading of both files: no static problem, and an empty candidate inventory (no storage rule, store, trigger or function of Supabase's side added). Every rule survives a dump and rebuild (on 26 Nov on `9cc35bf08`: 1,094 rules, 0 different; earlier, on 25 Nov: 1,085 rules, 0 different). The database tests are `supabase/tests/173-meeting-drafts-named-people.sql` (236 tests) and `supabase/tests/179-espacio-files-private.sql` (35 tests); `104-meeting-content-access.sql`, `145-meeting-finalized-stays-final.sql` and `130-visitors-list-no-store.sql` were adjusted to the new rule and policy.

Recovery without a destructive statement: the restrictive rule can be changed in place (`ALTER POLICY`), and each replaced function can be replaced again with its earlier body (`CREATE OR REPLACE FUNCTION`); the two routes need no table of their own, and older rows still hold an address the routes read.
