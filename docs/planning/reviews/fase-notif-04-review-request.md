## Where to look hardest
1. **URL precedence in `processNotification`.** The record path overrides a DB `url_template` for session, assignment, licitación and QA-run events. Events with no record route keep a safe template URL. Is overriding a live template acceptable before the sanitized trigger export exists?
2. **Fallback targets I chose for dead registry URLs:**
   - `message_sent` → `/community/workspace?section=messaging`
   - `user_mentioned` → `?section=overview` (the feed; there is no post anchor)
   - `meeting_finalized` → `?section=meetings`
   - `consultant_assigned` → `/profile`
   - `data_quality_alert` → `/admin/course-builder` (its producer still writes its own dead `/admin/course-assignments`, which is outside the allowlist)
3. **`recordId` accepts only a UUID or a positive integer.** Any other id (slugs, compound keys) falls back. That is deliberately strict.
4. **`emailFields` allowlists.** Actor display names (`sender_name`, `author_name`, `consultant_name`), `ganador_nombre` and record titles are allowed. Free text, grades, tester emails and recipient ids are not. `system_update` keeps `title`/`version`, not `description`.
5. **Role source and session routing (r2).** The `user_roles` lookup also changes admin links on other events: an admin now gets `/admin/feedback` (as before r1, via the old switch) and the `/admin/qa/runs/{id}` record. Session links for roles outside the detail page's list go to the narrower meeting page, not a detail view, so no session data widens.
6. **Unit size.** About 435 product lines and 1,150 test lines after r4 (r3: 410 / 930). Over the ~400-line guideline; the excess is required coverage.
7. **Per-recipient session access (r3).** `isSessionRecordOpenTo` passes `isFacilitator: false`; `canViewSession` does not read it, so a facilitator who is a school-scoped consultor at another school gets `/consultor/sessions`, exactly as the detail API would answer not found. The session row is read with the service role once per event; the recipient loop already reads `user_roles` per recipient. A `session.is_active === false` row links only for an admin, mirroring both pages. The DB template URL never applies while the payload identifies a session, so a template session link is only ever a fallback path and is denied without a resolvable session.
8. **URL classification choices (r4).** A mis-cased route is denied because Next.js routes are case-sensitive (the probe answers 404); the UUID is compared case-insensitively because the page's own validator and the DB uuid column are. One trailing slash is dropped (Next.js redirects it); `//` is denied. The family prefix covers only the two session page prefixes, so a typo such as `/meet/sessions/{id}` is a generic dead link the catalog never emits, not a session target, and stays outside this check. An authorized link keeps its query and fragment (a template author's `?from=bell` is harmless to the page) rather than being rewritten to the canonical path.

## Known limitations / deferred
- Not catalogued, because they have no `user_notifications` event type today: the legacy-table events in rev 3 (`quiz_reviewed`, `quiz_review_pending`, `group_invitation`, `reply_to_message`, workspace mentions) and `collaborative-submit` (it calls `createNotification` without `event_type`). They land with their D8/N2 producer migrations.
- `learning_path_assigned` and `meeting_finalized` have `audience: 'unwired'`: there is no recipient case in `getRecipients` (a known plan gap).
- `occurrenceId` returns null where the payload has no record id (`qa_scenario_assigned`, `data_quality_alert`). Consumers arrive in N2-01.
- The spec sends the session lifecycle producer's exact payload to `triggerNotification` instead of calling `notifySessionLifecycle`: that module's dynamic `import('../notificationService')` does not resolve under the Playwright transpiler.
- A template's query or fragment on a session link only ever survives on an event with no record builder (the `session_edit_request_submitted` admin case): whenever the payload names the session, the catalog record path outranks the template, so a lifecycle event stores the plain record link. Whether templates should be able to add a query to a record link is a template-policy question for the sanitized trigger export.
- A listed attendee outside the growth community receives the notification (the producer's recipient set is unchanged) but only a `/dashboard` link. Whether such attendees should be able to open the session is a session-policy question (an attendee rule in `canViewSession`), outside N1-01 and not widened here.
- **Release note for N1-03:** `system_update` is `off` in the catalog. Once the resolver reads it, system updates stop emailing by default. Today the live path still emails (a D5 test proves it).
