## How it works
- The database never sees an address. The worker computes `HMAC-SHA256(key, trim + lowercase(address))`, where the key is derived from the server-only `NOTIFICATION_SUPPRESSION_SECRET` (at least 32 characters, no fallback) and a purpose string, and hands over 64 hex characters.
- Before every attempt, and before `begin_notification_email_attempt`, the worker calls `check_notification_email_address(row, owner, digest)`. A first attempt passes the digest of the profile's current address and the database records it for the row; once the message is frozen the recorded digest is final, and a retry (which passes none) is judged by it. Answers: `clear`, `suppressed`, `unrecorded`, or nothing for an owner whose lease is gone.
- `suppressed` ends the row: `cancelled / address_suppressed` when nothing was frozen, `cancelled_after_ambiguous / address_suppressed` for a frozen retry. No key, a failed or thrown read, `unrecorded` or any other answer: nothing is sent and the row waits (`retry / suppression_unavailable`, frozen message kept).
- The webhook verifies the Svix signature over the raw body as before, then offers a bounce to both outboxes, recovery first: `record_password_recovery_delivery` (unchanged) and `record_notification_email_bounce(provider id)`. Only the provider id leaves the route; the recipient the event names is never read. The database suppresses the digest it recorded for the row that carries that id, so an id no row carries suppresses nothing. A delivered event is never offered to the suppression store, and nothing removes a suppression.
- A bounce can arrive before the worker commits the provider id. The evidence is stored (`pending`, answered 200), and `finish_notification_email('sent', id)` applies it in the transaction that stores the id. Both sides take the same per-id advisory lock, so whichever comes second sees the other's commit.

## Where to look hardest
1. **`finish_notification_email` was replaced in place.** It is the function every outcome of the worker goes through. Check that validation and the UPDATE are byte-for-byte N3-03's, that the added block runs only after the UPDATE applied, for `sent` with a non-empty provider id, and that nothing in it can make a successful send fail (the provider id index is not unique; an empty id is skipped). A failing suppression write does roll the finish back; the row then stays `sending` and is retried under the same idempotency key.
2. **The ordering race.** `record_notification_email_bounce` and the finish block take `pg_advisory_xact_lock` on the same hash of the provider id before they read each other's table. Check the lock comes before the evidence insert on one side and before the evidence read on the other, and the no-lock run in the race log.
3. **Which address gets suppressed.** Never one named by the event: the route forwards only `email_id`, and the SQL takes the digest from `notification_email_outbox_address` by provider id. The digest recorded for a row can be replaced only while nothing is frozen; check that branch of the check function, since a wrong digest there would suppress the wrong address later.
4. **Fail closed, and what that costs.** Without `NOTIFICATION_SUPPRESSION_SECRET`, or when the check cannot be read, no notification email is sent at all (rows wait; frozen ones end as `unknown` after 24 hours). The key is checked per row, not per run, because the unallowlisted cron-route test runs the worker without it. A changed key makes every stored suppression unmatchable: the addresses would bounce once more and be suppressed again.
5. **The webhook now fails on either store.** A bounce answers 500 when the notification write fails, also for a recovery message whose own transition succeeded (it is retried; both writes are idempotent). If the code ships before the migration, every bounce answers 500 until the function exists: the migration must be applied first.

## Known limitations / deferred
- The live synchronous sender does not read the suppression list (the order forbids changing it), and nothing sends through the outbox until N5-02. The digest sender (N5-01) must make the same check before it sends.
- A bounce can only be matched through a provider id the worker stored. A message whose first attempt got no answer and that never finishes as `sent` (it ends `unknown` or `cancelled_after_ambiguous`) stores none: its bounce stays as unmatched evidence and the address is suppressed only when a later email to it bounces. Matching by the event's recipient would close this, and is what the order forbids.
- `finish` applies only evidence that is still unmatched: a second row finished under a provider id whose bounce was already applied is not suppressed. A provider id does not repeat across rows (one idempotency key per row).
- The ordering guarantee relies on READ COMMITTED, the default of every call through the API.
- Only `email.bounced` suppresses. Complaints, and hard versus soft bounces, are not distinguished: Resend's bounce event is treated as permanent. There is no way to lift a suppression short of deleting the row with the service role; N4-02 owns the visible notice and any reset.
- Suppression is by exact normalised address (trim, lowercase). Provider-specific aliases (dots, `+tags`) are different addresses.
- A suppressed address still gets password-recovery and invitation mail: those do not go through this outbox.
- An outbox row is purged 90 days after it completed, with its address row; a bounce that arrives later than that matches nothing. Evidence is deleted after 90 days by the bounce function itself, not by the retention cron (`pages/api/cron/notification-email-retention.ts` is outside the allowlist), so it is only cleaned when bounces arrive.
- Every bounce also leaves recovery's own evidence row for a notification provider id (`pending`), as it already does for any id recovery does not hold; its retention deletes it after 30 days.
- The three tables hold keyed digests of email addresses: pseudonymised personal data of current-role users, no minor data. No consent/EIPD record was added; flag it if N3-06 needs one before cutover.
- `NOTIFICATION_SUPPRESSION_SECRET` is documented here only: no `.env*` file was edited. It must be set before N5-02 turns the outbox on.
- In the Playwright spec the worker runs inside the test process with a capturing transport: the app's cron route cannot send without a real provider key, and the real transport's URL is fixed. The webhook, the database and the login are the app's own. The spec is not in CI's mandatory list (`scripts/ci/e2e-mandatory.mjs`, outside the allowlist) and needs `RESEND_WEBHOOK_SECRET` and `SUPABASE_DB_URL`.
- The migration is applied only to the private `notif17isolated` stack, kept for PM review.
