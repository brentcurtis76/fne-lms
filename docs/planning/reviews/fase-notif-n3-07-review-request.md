## Objective and scope (from the order)
Make authorized notification email observable in the local E2E mail outbox for the synchronous sender and dormant worker. Correct the browser-boundary graph so type-only imports do not classify a server route and its mailer as browser code while runtime imports remain forbidden. Prove a synthetic recipient can see the notification through the app and captured email.

- **In:** the eight allowlisted paths (below).
- **Out:** content or recipient changes, preference UI/API, outbox cutover, digest, production flag enablement, schema, migrations, release. `lib/email/outbox.ts`, `lib/notificationService.ts`, every route, `middleware.ts` and every `.env*` file are untouched.

## How it works
- **Scanner.** `importSpecifiers` (the only input to the browser graph) now skips a declaration the compiler erases: `import type …`, `export type … from`, `export type * from`, and `import { type A, type B }` / `export { type A }` where *every* specifier is a type. A default binding, a namespace import, `import {} from`, a bare `import 'x'`, a mixed list, `export *`, `require()` and `import()` stay edges. The per-file rule `BROWSER_IMPORTS_SERVER_MODULE` is not changed: a browser file that names a server-only module, even by `import type`, is still flagged. `closure` is exported for the tests.
- **Effect on the graph.** 19 modules leave the browser set (705 → 686), all of them reached before only through type-only edges, `pages/admin/qa/assignments.tsx`'s `import type { QAScenarioAssignment } from '@/pages/api/qa/assignments'` among them: `lib/notificationService.ts`, `lib/notificationEvents.ts`, `lib/email/{notifications,outbound-policy,provider,render}.ts`, `lib/notifications/{catalog,resolve-preference}.ts`, six `lib/zoom/*` modules (`service-client.ts` among them), `lib/simulation/tenant-policy.ts`, `lib/types/tenant-kind.ts` and `lib/utils/{html-escape,meeting-dial-in,session-denials}.ts`. None was added (`RUN/evidence/logs/graph-diff.log`). They are now checked by the server rules only.
- **Sync sender** (`sendNotificationEmail`). After authorization, before `deliverOutboundEmail`: `if (authorization.kind === 'allow') captureOutboundEmail({ to, subject, html })`. The sender was already validated at the top of the function. Same contract as `lib/email/invitations.ts`: the mirror is additive and says the message was *handed to the provider boundary*, so it is written even when no provider key is configured (which is how the local e2e sees it).
- **Worker.** After `begin_notification_email_attempt` and `openSnapshot`, just before `deliverOutboundEmail`: the frozen `to/subject/html` are mirrored. Every earlier exit (access, preference, QA, refusal, no provider key, recovery priority, suppressed address, lost lease, unreadable snapshot, 24-hour timeout) happens before it, so only an attempt that reaches the provider leaves a line; an ambiguous attempt and its retry are two attempts and leave two identical lines.
- `outboxPath()` still refuses on `VERCEL=1` / `VERCEL_ENV=production` and is inert without `E2E_MAIL_OUTBOX`; `captureOutboundEmail` never throws.

## Where to look hardest
1. **The scanner change weakens a security gate by design.** 19 modules stopped being checked by the browser rules. Check that every one of them is really reachable only through a type edge (the graph diff), and that `isTypeOnlyDeclaration` cannot be fooled: an `import X, { type Y }`, an `import {}` and an `export { type A, B }` must stay edges (tests pin all three). It relies on TypeScript eliding `import { type A }` entirely, which holds while `verbatimModuleSyntax` is off (`tsconfig.json` has `isolatedModules` only); turning it on would make such an import a side-effect import the scanner no longer sees.
2. **`import type` of a server-only module is still flagged per file.** I left `BROWSER_IMPORTS_SERVER_MODULE` untouched, as the order says not to loosen server-only rules. It is stricter than the bundle needs; a reviewer may prefer that.
3. **What a mirror line means.** Both senders mirror an attempt handed to the provider boundary, not an accepted message: a definite refusal and a not-configured sync send still leave a line, like invitations. A retry of an ambiguous worker attempt leaves a second identical line. Check that this matches "once per eligible attempt" and is not a "misleading artifact".
4. **The worker's mirror has no guard of its own.** It relies on every refusal path returning earlier (authorization, sender, config, suppression, lease). Mutants moving it earlier are caught, but a future edit that reorders `processRow` would change it.
5. **The e2e uses the sync path only.** The dormant worker cannot send in the app server without a provider key, so its mirror is proven by the Vitest suite, not in the browser.
