## 5. Where an independent reviewer should look hardest

1. **`settle_learning_path_sessions` and the two functions that call it** (migration 120000 §6b): the data-modifying CTE chain (`claimed` → `settled` → `totals` → `credited`) relies on Postgres executing unreferenced data-modifying CTEs; the proof script and pgTAP 070 §6b exercise it, but review the SQL for the group-member case (no assignment row → settled without credit) and for `last_activity_at` monotonicity.
2. **Column-level grants on sessions** (120000 §5): `session_data` is client-writable on INSERT/UPDATE (jsonb, no product writer found) — kept to avoid breaking an unknown consumer; a reviewer may prefer to drop it.
3. **`auth_is_backend_caller`** (120200): the rule "no JWT claims at all counts as backend" admits any direct database session; that is the seed-script path. Confirm this is acceptable versus requiring the explicit `service_role` claim only (which would break `psql`-driven seeds).
4. **Discussion INSERT policy for school-scoped groups** (120100): with `community_id NULL` the workspace relation is not validated (documented limitation).
5. **R6 audit-log filtering**: non-admins get only `content_type = 'course'` rows and lose `source_learning_path_id`/`sourceLPName`; the `source` value (`'learning_path'`) on a course row is still returned (it names no path). Confirm this reading of "no learning-path data".
6. **Backfill `UPDATE` in migration 120000** (marks historical closed sessions settled): the only row-data change in the release; justified to prevent double credit — see the rollout doc §4.
7. **`createApiSupabaseClient` Bearer branch** (`lib/api-auth.ts`): every API route that accepts Bearer auth now runs its queries as the token's user instead of `anon`. This is the intended parity, but it changes what those routes can read/write for Bearer callers (they gain the user's RLS view; they lose nothing anon had, since anon has no grants on the remediated tables). Review whether any route relied on the anon view.
8. **E2E fixtures created through the service-role client** inside the spec (instructor, two courses/modules/lessons, one workspace for the fixture community) and removed in `afterAll`: matches what auth-lifecycle / network-supervisors do; confirm.

## Material design choices (reviewer to confirm)

1. **Final settlement after revocation is clipped, not refused.** `end` on a revoked learner's open session closes it at `greatest(last_heartbeat, session_start)` (heartbeats need authority, so that mark cannot be advanced) — the earned interval is credited once, the unauthorized tail is not. Refusing `end` outright would leave an open session the learner cannot close (only maintenance could).
2. **Lock order, not retries.** The cycle is removed by making every writer take the pair advisory lock first; the maintenance batch is bounded to 500 candidate sessions per run (advisory locks per transaction stay small; the route is idempotent and re-runs). Concurrent maintenance runs on the same pairs now serialise instead of taking disjoint rows; exactly-once is unchanged.
3. **Copy, never sum.** Every reconciliation between the progress record and the direct mirror copies values into whichever record is new; increments are applied to both. A pair with several direct rows (no UNIQUE exists) is seeded from its richest row. The mirror does not receive ad-hoc direct increments made outside the session functions (unchanged from R2; the proof's +7 documents it).
4. **First-value semantics for `started_at` / `completed_at`.** The record keeps the first value; the old activity route re-stamps `completed_at` on every `path_complete`, so during the deploy window the mirror's timestamp can trail the record's by seconds (completion *state* agrees; rehearsed).
5. **Legacy folder rows are left alone.** The guard fires only for INSERT and for UPDATE OF `parent_folder_id, workspace_id`; a legacy foreign parent is invisible in the breadcrumb, a legacy cycle above a folder makes new children under it fail (`23514`, bounded walk) — that folder is broken data for the owner, not something to rewrite silently. `community_documents.folder_id` across workspaces is a separate, unreviewed relation (not part of R3-03).
6. **The maintenance close settles closed-but-unsettled sessions.** Only the old cleanup route can create them (window artefact); crediting them once, union-clipped, on the first new run is safe because the migration backfill already marked every pre-migration closed session settled.
7. **`enhanced-progress` now reports real figures.** The route previously hard-coded `totalTimeSpent: 0` and `currentCourse: 1`; it now reports the record. Pages `my-paths/[id]` and `mi-aprendizaje/ruta/[id]` consume these keys (read-only inspection; not driven in a browser).

## Material design choices (reviewer to confirm)

1. **Two-tier heartbeat invariant, one trigger.** Application principals never choose the heartbeat value (replaced by `now()`); trusted writers may backdate but never post-date (clamped). The distinction is `current_user` inside a non-SECURITY-DEFINER trigger function — `authenticated` for a direct PostgREST write, the function owner inside the SECURITY DEFINER RPCs (which write `now()` anyway). The backdate allowance exists for fixtures and maintenance only; it can only reduce credit.
2. **Pre-guard future heartbeats count for nothing, and are not rewritten.** `lp_last_authorized_heartbeat` treats `hb > clock_timestamp()` as no evidence and uses the session start (`clock_timestamp()`, not `now()`, so a heartbeat committed by a concurrent transaction that began after the caller's is never mistaken for a future value). The migrations do not touch stored values (rollout postflight Q6 records how many open sessions carry one). A learner who still holds authority is unaffected (closed at `now()`); one who lost it, or the maintenance close, credits nothing beyond the start for such a row — conservative by design, and an operator data question rather than a reconstruction from a client-controlled timestamp.
3. **Reconcile, don't quiesce.** The legacy write set is small and fully known (three columns, one route), so a trigger that copies it into the record is safer than a cutover interval that would have to be enforced operationally. Copy semantics mirror R3-04: sequence is a position (copied, including a step back), completion is first-value, last activity monotonic. Totals are never summed.
4. **Lock order extended, not changed.** Every session writer already held `advisory → session rows`; the assignment-before-progress step is now explicit in `lp_record_progress` and shared by the AFTER ROW trigger path (which necessarily holds the assignment row first). The proof observes the second writer waiting on the assignment row (`transactionid`) in both orders with no `40P01`.
5. **The mirror-write flag is a transaction-local GUC**, set and cleared around the one mirror UPDATE (`lp.mirror_write`); a failed statement rolls the setting back with the transaction. pgTAP asserts it is cleared after a settlement.

## C.2 Design summary (details in the three `docs/reviews/rls-*-2026-09-07.md` documents)

- **Actor binding** (`auth_actor_bound`): honour a caller-supplied user id only for self, a literal admin, or a trusted backend (`auth_is_backend_caller`, never `current_user`); safe negatives, never an exception inside a policy; grants kept where a policy can be evaluated by anon (8 public-targeted policies).
- **Entitlement is live, provenance is stored**: `access_origin` records how a row was created; access for a `learning_path` row is evaluated against the CURRENT direct/group entitlement to that course through any path. No revocation write, so retries, partial failures and reassignment cannot desynchronise access from assignment. `unknown` rows keep access (explicit unresolved state); nothing historical is guessed or deleted.
- **Reporting**: simplest correct design — live views for everything derivable from durable tables, one durable per-(path, user, day) grain for session activity (written exactly once per settled session under the settlement locks), owner views with in-view filters plus API gates for service-role readers.
- **Retention**: delete only what is neither settlement evidence nor unrecorded reporting evidence, bounded, idempotent; the response says what was retained and why.
