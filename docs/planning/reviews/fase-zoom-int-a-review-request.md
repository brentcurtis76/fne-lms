## 5. Migration / trigger / function security design

- **Classification vs. enablement.** `tenant_kind` (client | operator | qa) is durable classification; `internal_zoom_testing_enabled` is an insertion-only runtime switch. Both default safe. The CHECK is validated against every existing row (all `client`), so an unclassified school cannot exist.
- **`public.enforce_operator_session_tenant_guard()`** — `LANGUAGE plpgsql`, `SECURITY INVOKER`, `SET search_path = ''`, every reference schema-qualified. Resolves `NEW.school_id → public.schools`. **Fails closed** on NOT FOUND (23514, constant message). For an operator tenant: on `INSERT` only, refuses while the switch is false; then refuses non-NULL `contrato_id`, `hour_type_key`, `program_enrollment_id` independently (INSERT and the relevant UPDATEs). `client` and `qa` pass through untouched. No modality/Zoom/facilitator/roster/approval rule.
- **`public.enforce_operator_ledger_guard()`** — same shape. `session_id IS NULL` passes (manual rows). Resolves `NEW.session_id → consultor_sessions → schools`; fails closed on NOT FOUND; refuses whenever the tenant is `operator`. Fires on `UPDATE OF session_id, allocation_id` because they are independent foreign keys: exposed roles cannot update either today (column-scoped grants, 20260813120900), but the owner and other privileged writers can, and none may associate an operator session with a contract allocation. Reads no other ledger column.
- **Error contract.** Every rejection is SQLSTATE `23514` with one of seven constant, deterministic, non-PII messages (no interpolated ids/names/emails); the pgTAP suite pins all seven byte-exact.
- **SECURITY INVOKER + RLS.** The tenant lookup runs under the invoker's row level security: authenticated users see every school through `schools_read_authenticated`; admins see every session; `service_role`/`postgres` bypass RLS. A row hidden from the invoker behaves like a non-existent one and is refused, never treated as `client`. Deliberate consequence: a non-existent `school_id` / `session_id` now fails with the guard's 23514 before the FK's 23503 would have fired (pinned by E25 and F6). Trigger functions cannot be invoked directly (`0A000`), so the schema-default EXECUTE that Supabase's `ALTER DEFAULT PRIVILEGES` gives every new public function (identical to `protect_must_change_password()` and `set_updated_at()`) grants nothing usable; the migration issues no GRANT/REVOKE.
- **Additivity / rerunnability.** `ADD COLUMN IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, catalog-guarded `DO` blocks with the DDL executed directly (no `EXECUTE` string literal); re-application is a no-op. Ordering on `consultor_sessions`: BEFORE ROW triggers fire alphabetically, so `trg_consultor_sessions_updated_at` precedes the guard; no interaction.

### 7.1 Blocking finding — the ledger-authority registry (outside the authorized boundary)

`__tests__/lib/services/ledger-hours-reader-inventory.test.ts` is a governance registry: it statically analyzes every migration and requires an explicit classification for anything that could carry ledger authority. Two of its rules fire on this migration, and a throwaway diagnostic copy of the test (written beside it, run once with `-t "discovers active raw-hours"`, deleted immediately, never staged) confirmed the exact strings:

1. `ledger trigger authority requires explicit classification` — `schemaLedgerUnsupported()` matches **any** `CREATE [OR REPLACE] [CONSTRAINT] TRIGGER … ON public.contract_hours_ledger`, top-level or inside a `DO` block, after comments and string literals are stripped. Plan §4.2 makes the ledger guard mandatory, so no compliant shape of this unit avoids the entry; routing the DDL through a dynamic `EXECUTE` to dodge the regex would be evasion of a governance scanner and was not attempted.
2. `ledger-relevant statement could not be classified` — the catalog-guarded `DO` block that creates the ledger trigger is one statement (up to its first `;`) that carries both a `SELECT` (the `pg_trigger` existence check) and the ledger name, is not ledger-backed, and counts zero hours uses. A top-level `CREATE OR REPLACE TRIGGER` would remove this second entry only; the first remains.

The registry is `SQL_UNSUPPORTED_EXECUTES` in that test file. The task authorization forbids editing "other tests", so the executor stopped rather than widening scope. **Minimal remedy, for Brent to authorize separately:** add one entry for `supabase/migrations/20260902162557_fne_zoom_operator_tenant.sql` with two classification strings (the test compares only the entry count per path; the strings document the authority), for example `'enforce_operator_ledger_guard:trigger-authority/refuse-only'` and `'enforce_operator_ledger_guard:guarded-create/no-ledger-read'`. The guard reads no ledger column and can only refuse a write (§5), which is what those labels record. Until that entry lands, CI Gate 2 is red on this branch by design of the registry, not because the schema is wrong.

## 10. Areas an independent reviewer should scrutinize hardest

1. **The insertion-only enable switch.** `internal_zoom_testing_enabled` is checked only when `TG_OP = 'INSERT'`. Consequences the reviewer should weigh: (a) disabling it never blocks lifecycle updates to an existing operator session (E27/E28 prove this — including an UPDATE that fires the guard); (b) a NULL-financial session can be *moved* into an operator school by `UPDATE … SET school_id` regardless of the switch (E21 proves the move while enabled; the disabled-move case is deliberately not asserted). The plan defines the switch as creation control only; if the reviewer wants moves gated too, that is a design change, not a bug in this implementation.
2. **The relevant UPDATE column set.** The session trigger fires on `UPDATE OF school_id, contrato_id, hour_type_key, program_enrollment_id` only. A status/approval/finalization update does not fire it at all (E27). Confirm that set is sufficient: it covers acquiring a financial field, stripping it (allowed), and moving across the tenant boundary (E19). Nothing else can change the tenant of an existing session.
3. **`allocation_id` / `session_id` independence.** F12 proves the `allocation_id` event on its own — a client session with its ledger row, the school reclassified to operator with history in place (no trigger on `schools`, by design), then an allocation change that names neither `session_id` nor a session at all is refused; F14–F17 prove repairs away from the operator state stay open. Exposed roles never reach this event today (42501 column grants precede triggers), so the proof necessarily runs as the owner — confirm that is the binding the plan asks for.
4. **The surgical 017 re-pin.** Diff `supabase/tests/017-…` against the base: exactly one assertion (4 lines → 5 lines), `plan(63)` untouched, everything else byte-identical. The old assertion pinned "zero BEFORE triggers on the ledger"; the new one pins "zero BEFORE-trigger functions on the ledger whose source mentions `effective_minutes`". A BEFORE trigger that assigned that column through a name-free path (e.g. record manipulation) would not be caught by the regex — the same class of limitation the sibling `SET[[:space:]]+effective_minutes` assertion already has, and 063 B19 cross-pins that neither guard body contains the token.

Verify the three consequences: (a) an authenticated admin is served and bound (E22/E23, F1/F2); (b) `service_role` and the owner are bound (E24, F4/F5); (c) unresolvable rows are refused with 23514, which changes the SQLSTATE a non-existent `school_id`/`session_id` produces from the FK's 23503 (E25, F6 pin this deliberately).
